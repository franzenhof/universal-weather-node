# To-do / Roadmap

Open work and ideas for the Universal Weather Node. Done items move to the [Changelog](CHANGELOG.md).

## Roadmap (agreed 2026-11-22)

**Two lines:** 2.x stays the firmware for the Heltec **V3 and V4**; the next major version, **4.0.0**, is **V4 only** (ESP32-S3R2 with 2 MB PSRAM) and gets the new framework, the better web server and a much bigger dashboard. The V3 has no PSRAM — it is what held back both the framework update and the web server (see [background](#next-major-version-background-framework-and-web-server-experiments)).

### 2.0.0 — stabilise sensors and system

**Released 2026-11-22** (decided with most exit criteria met; the open ones — tester field tests, PSRAM on a real V4, long heap runs — continue on 2.0.x). **Branches (2026-11-22):** `2.x` = the 2.0.x line (fixes, tags `2.0.1` …), `1.x` = the 1.x line from tag 1.1.1 (archive, no fixes planned), `main` = the next major version (work starts when the own Heltec V4 arrives).

Exit criteria (2.0.0 final only when all are met):
- [ ] Tester field tests done: Ecowitt values compared with the console, WS90 reception rate explained (rc.9 trace), Davis on site
- [ ] no open crash / restart report
- [ ] free heap stable over several days on the test node (HTTPS uploads, many wireless sensors, radio trace)
- [ ] PSRAM confirmed running on a real V4 (status page / `system.psram`)
- [ ] docs and README match the firmware

**Done in 2.0.0: custom series** ("eigene Messreihen") — values that are not one of the main weather values (soil moisture, lightning, leaf wetness, PM2.5, CO₂, soil EC, a DS18B20 …) get a chart: a free-text name, a source (wireless sensor ID + value, or a board probe) and a fixed aggregation per value (mean; lightning: strikes per bucket from the running counter; distance: minimum). Rings only for defined series (int16, ~0.9 KB each for 24 h + 7 days), V3 up to 4, V4 with PSRAM up to 8; the 7-day tier is saved with the history as now (cfgdata NVS, 16 KB reserve). Then the last rc.9 or 2.0.0 directly.

Afterwards: branch **`2.x`** (created 2026-11-22 from `main` right after the 2.0.0 tag, which only added a docs entry) — small fixes there, or back-ported from the next major version (cherry-pick). `main` is the next major version. V3 users get fixes on 2.x for a stated time (decide: e.g. 12 months).

8. **Davis 6450 solar radiation sensor in W/m²** (V4 Full, AUX analog `AIN`): today the AUX input shows only a voltage. Add a mode "Davis 6450" for the AUX input that converts to W/m² and feeds the existing solar value (`{solar}`, history, MQTT / Home Assistant, weather networks, LoRaWAN) like the wireless Davis ISS does; check the reading against a reference (or a wireless sensor's light value) before release. Mentioned in [Example Setups](docs/example-setups.md) (setup A).
9. **Sensor emulation / protocol bridge** (4.x — a real use case, decided to build; reversed the 2026-11-23 "don't build" after the console/dashboard problem showed the benefit). The node transmits its own measured / source values as a small set of **Ecowitt sensor frames** (e.g. wired Davis wind/rain or a BME280 appearing as a WH31 / WS69 / WH40), so the user can pick whatever console, app, gateway, cloud or FOSHKplugin they like and it runs with almost any sensor the node receives. Also handy as a test-sensor simulator. **Why this is safe, and the hard red line:** sensor frames carry only readings — spoofing a reading is low stakes and already possible with an SDR. The real danger is actuator / gateway *commands* (open a valve, switch a socket). Therefore: (a) **only sensor frames built from the node's own values — no raw "send these bytes" path in the code;** (b) **no actuator / gateway frame builders in the repo at all** (a patcher would have to write that protocol themselves — the SDR-level barrier we want to keep; the dangerous capability simply never exists in the code to uncomment); (c) **own fixed ID, never a foreign sensor's ID** (no hijacking a specific neighbour sensor); (d) **off by default.** 868 MHz SRD duty cycle (1 %) is fine at one packet per 16–60 s. This is independent of the Ecowitt IoT analysis with Dirk (that only concerns actuator commands, which we never build).
   - **Design (user, 2026-11-24):** offer a handful of **virtual sensor types** (WH31, WH40, WN32P, WH65, …); for each, the user **freely maps every frame field to any value the station has** (a received wireless sensor's value, a board probe, a derived value). So a manufacturer-A sensor's reading can be re-emitted as a virtual manufacturer-B sensor — e.g. a Bresser or Davis temperature sent as an Ecowitt WH31. The typed encoders below are the building blocks; this field-mapping is the config layer that comes with the transmit path.
   - **Status 2026-11-25:** the **frame encoder is built and host-tested** (`lib/FineOffsetSensorReceiver/src/FineOffsetEncoder.*`, `test/firmware_foencode.cpp`): WH31 (temp/hum), WH40 (rain), WN32P/WH25 (temp/hum/pressure, for a BME280) and **WH65/WS69** (the 7-in-1: **wind** speed/gust/direction + rain + temp/hum + UV + light, for a wired Davis ISS) are round-tripped through `foDecode`, so the byte layout, CRC-8 and checksum are proven correct against the validated decoder. No raw-byte path, no command frames — the red line holds. **Still to do (V4-only):** the FSK transmit path (SX1262 TX, PA via the front end from Heltec's `radio.c`, radio shared with RX / LoRaWAN, duty cycle), the field-mapping config (per virtual sensor: type, own ID, interval, and a source for each field), and over-the-air verification with a real receiver (our own RX or Dirk's gateway) before release.
   - **Status 2026-11-26 (C1):** transmit path, field-mapping config (4 slots, ID derived from the MAC), duty-cycle ledger shared with LoRaWAN, status page + `/api/info`, docs ([docs/virtual-sensors.md](docs/virtual-sensors.md)) built and host-tested; red line guarded by `test/firmware_vsensor.cpp` + `test/vsensor_guard.test.js`. **Open:** over-the-air check (V3 test node as Fine Offset receiver, then Dirk's gateway); FSK deviation (50 kHz) not measured on an original.
   - **Use-case idea (Dirk, someday):** analog→Ecowitt bridge — read an analog sensor on the AUX `AIN` (item 8) and re-emit it as a virtual sensor, so an arbitrary analog signal lands in an Ecowitt gateway/console; a dedicated multi-input board (more ADC channels, 4–20 mA, isolation) would extend this. Pure future music.
   - **Repeater (decided 2026-11-25):** the dead-spot ("Funkloch") case is covered by the own-ID virtual sensor (map a received sensor's values to a virtual sensor with our own ID → appears as an extra sensor at the gateway). A *transparent* repeater (re-emit under the sensor's original/foreign ID) is **not pursued** — it would send a foreign manufacturer ID and is the start of capture-replay; that "re-send a received packet under a foreign ID" path must not exist in the code. Revisit only on a very strong concrete need.
10. **Live instantaneous values on the display** — **done 2026-11-24/25** (CHANGELOG 4.0.0, "Live values on the display"). Nothing open.
11. **Auto-search: ramp the lock threshold instead of a hard step** — **done 2026-11-26** (threshold = base − 15 dB · t / 30 min, 3 packets in 10 min still required, strongest window mean wins; `rf_autosearch.cpp`, tests in `firmware_rfautosearch.cpp`). Original idea (4.x): today auto-search needs `AUTO_MIN_RSSI` (−105 dBm on V3, −85 on V4) to lock a sensor type, and only after `AUTO_WEAK_AFTER_MS` (30 min) does it take the best weak candidate (rf_autosearch.h). Instead, lower the threshold gradually over the window: strict at the start (a strong own sensor still locks at once), relaxed toward the noise floor by the end (a moderately weak own sensor locks after a few minutes, not the full 30; a very weak neighbour / noise only near the end). Needs no config value and is board-agnostic (the ramp runs relative to the base threshold, the V4 +20 dB offset is already in it) — this replaces the idea of a raw dBm expert setting or a "search sensitivity" toggle. Keep `AUTO_MIN_PACKETS` (3 in 10 min) so a single noise blip never locks, and pick the strongest candidate above the current threshold (`bestRssi` / packet counts already exist).
12. **Screensaver screen for burn-in protection** (4.x, V4): a screen that briefly takes over the OLED every few minutes for a few seconds, so the always-static elements rest. **Pixel-shift was rejected** — a full-width element (e.g. the title divider line) stays in almost the same row after a 1–2 px shift, so only a screen that *replaces* the content actually rests those pixels. Fun content, data-driven: a little figure that walks across the screen (also moves the lit pixels around) and **reacts to the current values**, with a *pool* of little animations per condition picked with some randomness (plus rare surprise ones) so there is always something new to spot — the variety is the point, a running gag you keep rediscovering. All from data the node already has: cold / frost (<0 °C) shivers in a scarf, breath puffs, builds or throws snowballs; thaw (rising back above 0 after frost) snow melts, splashes in the slush, sheds the coat; mild strolls; hot sweats and fans itself, grills, mixes a cocktail, sunbathes; high UV index rubs on sunscreen; rain (rain rate / rain today) umbrella, puddles; gusty wind clings to a mast so it isn't blown away, hat flying; lightning (WH57) a bolt, runs for cover; fog / high humidity a flashlight, tries to light the way; bad air (WH41 / WH43 / WH45 / WH46 PM2.5 / CO₂) coughs, covers its face / puts on a mask; dry soil (WH51 low moisture) waters the plants with a can; night moon, yawning, sleepy. Uses only values the node already has; small sprites, cheap on 128×64 mono. Options: on/off, interval and duration. **Mode as a combobox** (*Settings → Display*): off / brief blank / moving dot / walking figure / weather icons (sun → cloud → rain). The takeover itself is what rests the pixels; the figure is only the fun variant, the blank / dot give the same protection for gag-haters. A brief blank every 12 h does **not** help (burn-in is about cumulative lit hours, not a rare blink) — the real levers are the existing **night-off** (hours of rest daily), **lower brightness** (contrast setting), and letting the screens **auto-rotate** so the same pixels aren't always lit. Animated screen transitions (slide / wipe / fade) would be nice polish but barely help burn-in — the content *changing* is what helps, not how it transitions. New feature → `main` / 4.x only, not `2.x`.
13. **Dashboard escalation** (4.x): grow the LAN dashboard, but the node only *serves data* — charts render in the browser, truly heavy / long-term dashboards go to Grafana via the Prometheus endpoint (item 7). Stays LAN-only (the public dashboard is a separate project). Tiers:
    - *Quick wins:* **"today at a glance" card** and **day/night shading** on the trend charts are **done 2026-11-24/25** (commits "Dashboard: 'Today at a glance' panel (4.x)" and "Dashboard: day/night shading on the trend charts (4.x)"). `include/chart_page.h` already contains sparkline cards and a wind compass + rose (grep: header comment, "Metric cards (big number + sparkline)", "Wind compass + rose"). Not verified: whether sunrise/sunset markers are on the charts, and whether the rose also shows speed.
    - *Medium:* **long zoomable history** from PSRAM (24 h / 7 d / 30 d / year, pan + zoom, downsampled on the node — raw recent, aggregated older) with **period compare** (this week vs last) — **node side done 2026-11-26** (B2: tiers 5 min / 1 h 35 d / local days 2 y, `range=30d|1y`, `end`, `res`; open: the dashboard UI); **per-sensor pages** (each of up to 32 wireless sensors: history, battery, reception); **live push via Server-Sent Events** (the new esp_http_server) so tiles update instantly instead of polling; **CSV export** for a range.
    - *Ambitious:* **configurable layout** (user picks tiles / order / groups outdoor-indoor-soil-air, like the custom OLED screens but for the web); **chart annotations** (rain / storm markers, alarm thresholds as lines); **mini local forecast** (Zambretti from pressure tendency + lightning/gust for a storm hint, not a real forecast); the **weather figure** from the screensaver could live on the dashboard too.
    - Recommended first step: wind rose + sparklines + "today at a glance" + live push (SSE) + zoomable history with compare — the biggest visible jump for the effort, all client-side, the node just serves JSON. New feature → `main` / 4.x only.
14. **MQTT / REST sensor source (input)** (4.x) — **built (C2), device test open** ([docs/network-sensors.md](docs/network-sensors.md)) — model a network-sourced sensor as a **first-class value source**: a topic→field mapping that writes into the same store as the RF sensors (via `rfStoreValues` + the freshness window). Then the whole existing pipeline consumes it **for free** — OLED custom pages + placeholders, dashboard, history, `/api/data`, MQTT-out, Home Assistant, weather networks, LoRaWAN, and as a source for the virtual-sensor TX (item 9). Symmetric to the TX encoder: mapping **in** vs mapping **out**. **Reframes the old "direct-only" rule** (1-Wire / 868 / MQTT are all just transports; the node only truly measures wind/rain pulses + board ADC): network input is allowed as a **clearly-labeled, opt-in, expert** source; the node stays primarily a measuring station (works fully without it). Not hand-holding: an MQTT sensor is just a **normal source** — what reaches the weather networks is governed by the ordinary source selection, exactly like a wireless sensor; mis-configuring it (e.g. sending a remote temperature to AWEKAS) is the user's call, same category as a badly-placed sensor (GIGO). The only genuinely useful extras are about clarity/correctness, not policing: **label the source as MQTT/remote** (provenance visible) and a **staleness guard** (a dropped VPN must not freeze a stale value as current, like a dead sensor). Driving use case: a second own station (Rannungen, ~200 km, too far for LoRa) shown on the home dashboard over VPN + MQTT. A pure "just display my other station here" need can also be met at the dashboard layer (the separate public-dashboard project) without node-level ingestion.

Hardware alongside: at least **two own V4 (S3R2)** as test nodes before milestone 1; the V4 Full (formerly PCB v2.0) dropped the V3 socket set in Rev 1.0.

- **Ecowitt field test (Heltec V4.2):** compare values with the console (dew point, feels-like, relative pressure, rain amounts). Radio trace of 21 Nov (forum #41, rc.8, 21 sensors) evaluated: every decoder gives stable, plausible values (real frames are now host tests); WN32 / WN32P confirmed as 8-byte frames with only the sum at byte 6 (byte 7 constant per sensor, meaning unknown); DP70 / WH55 arrives at the normal 17.24 kbit/s; send intervals match the nominal table. Losses come in runs (up to 114 s) while other sensors are received. rc.9 traces show the expected-vs-received rate per sensor and the read delay (packet interrupt → firmware); next: a trace from the WS90 owner, then look at frame variants / timing.
- **Davis Vantage Pro2 / Vue field test** (frequency offset, channel table, supercap / solar scaling)
- **WS85 / WS90 rain:** raw total since reset, rain-start / wet bit, 16-bit counter overflow, rate-dependent piezo gain
- **WN20 rain correction** (Ecowitt wiki, section WN20, read 2026-11-21): real tip volume ≈ 0.28 mm, but each tip is counted as 0.3 mm and every sixth as 0.4 mm (over-read); the sensor sends this 0.1 mm total (`be16 × 0.1` in our decoder), so we inherit it. Wiki workaround: gain **0.908** up to 5 mm/h, **0.773** at 5–10 mm/h, higher rates still being measured (a linear decrease is expected). Funnel 0.00523 m². → in rc.5: per-sensor gains (rain, wind, UV, light) and an optional rate-dependent WN20 preset (default off); rc.6 docs: plain factor 0.908 is the recommended way, the preset is experimental. Open: factors above 10 mm/h once the wiki has them.
- **Bresser and Ecowitt / Froggit together:** timed switching built in rc.6 (`src/rf_schedule.cpp`, simulation 98–100 % of the packets) — field test with both brands pending (forum #16 / #20, luftstrom)
- **WS90 / WS80 pressure:** arrays with the newer SHT30 T/RH/P module also report pressure (Ecowitt wiki) — not decoded yet; need a radio trace from an owner
- **WH57 counter semantics:** the wiki says "number per transmission interval" (and the 79-s interval restarts at a strike); testers' values (89 / 137 / 242) look like a running counter, and the 21 Nov trace confirms it: 89 in every packet for 15 min without a storm (distance 255) — it does not drop to 0. Lighter-spark test would still settle whether one strike adds exactly 1
- **LDS01 (laser distance):** decoded since 2.0.2 (family `0x54`, 19 bytes, every 80 s, about every 10 s for a while after a change): distance = low 12 bits of bytes 6–7 (mm), byte 15 = low byte of the console's heat-on count. Matches Dirk's trace of 2026-11-25 (496 / 751 / 1001 / 751 / 501 mm, count 293–297). Bit `0x40` of byte 6 is set only in the 10-s frames (fast-send flag, inferred; first taken for "heater on" — wrong). **Open:** (a) in the 21 Nov trace the console showed 1328–1332 mm, the frames 1321 / 1322 (offset setting in the console? other time?); (b) the upper part of the heat count — all traces so far are 256–511 (282, 293–297), asked Dirk for one below 256 or from 512; (c) byte 4 (`8C` / `8B`, 20 mV steps would be 2.80 / 2.78 V), bytes 5, 11–14, 16.

## Next major version: background (framework and web server experiments)

Measurements behind the roadmap; both items return in the next major version (milestones 1 and 3).


1. **Web server → `esp_http_server`: postponed, the Arduino `WebServer` stays for now.** Prototype 2026-11-22 on Arduino-ESP32 2.0.11 (which ships `esp_http_server` from ESP-IDF 4.4), next to the WebServer on port 8080, 8-KB task stack, at most 4 connections:
   - RAM is no obstacle: `httpd_start` 13 KB (8 KB stack + ~5 KB), ~1 KB static; minus the `webApi` task (8 KB) and the WebServer object about 3–5 KB more in total. 12 parallel 20-KB pages plus old-server pages: all answered, ≥ 88 KB free in the handlers.
   - limits work: header too long → 431, URI > 512 B → 414, 100 KB of header garbage rejected without restart or heap loss.
   - blocker: the request-header limit of 1024 B is compiled into the 2.0.11 library and applies to the whole header block (2 × 600 B → 431). A Chrome request with Digest login is ~990 B — a longer Referer / URL or one more header would lock the settings pages out with 431. Way out: vendor `esp_http_server` from ESP-IDF 4.4 (Apache-2.0) with e.g. 2048 B (~1 KB RAM more); untested whether it links cleanly next to the built-in library.
   - porting work (42 routes): own Digest authentication (MD5 from mbedTLS, nonces), no multipart parser (OTA / backup upload: send the raw file body instead), POST form bodies read and URL-decoded ourselves, response header strings must live until the response is sent. The setup portal keeps WiFiManager's WebServer.
   - if picked up again: first the vendored library with the larger header limit, then the routes.
2. **Arduino-ESP32 3.x (ESP-IDF 5): postponed while Heltec V3 nodes are supported.** Experiment 2026-11-21 (branch `framework-arduino3`, pioarduino 55.03.313 = Arduino 3.3.13 / ESP-IDF 5.5, kept as reference, not merged): ported (PCNT on the new `pulse_cnt` driver, LEDC, task watchdog, miniz, HWCDC, `WiFi.h`), builds without warnings, host tests pass, runs on the V3 test node (old and new bootloader, erased first start, wireless reception, web pages). Rejected because of RAM on the V3 (no PSRAM), measured with the same diagnostics in both builds, 90 s after the start:
   - free heap 137 KB → 102 KB (about 94 KB after hours), largest free block 127 KB → 61 KB (about 35 KB after hours); web-task stack 1.5 KB tighter.
   - where it goes: ~5.5 KB smaller heap from the start (static RAM / IRAM of the framework), ~7.7 KB larger system-task stacks in the 3.x sdkconfig (esp_timer 4 → 8 KB of which over 7 KB unused, lwIP 2.5 → 4 KB, IPC 2 × 1 → 2 KB), ~14 KB more used during `setup()` (not narrowed down: Arduino 3.x network layer, new IDF 5 drivers, pin manager), ~7 KB more for Wi-Fi bring-up and runtime. Wi-Fi buffer settings are the same in both. Bluetooth is no lever: 3.x already releases the BT memory at the start (2.0.11 did not).
   - recoverable at best ~10–15 KB (system-task stacks via pioarduino `custom_sdkconfig` = rebuilding the framework libraries, smaller own task stacks), not the 2.x level.
   - also found: once after the update the stored Wi-Fi config allowed WPA3 SAE with H2E only → reason 210 against the WPA2/WPA3 access point (guard `fixLegacySaePwe()` on the branch); pioarduino overwrote `.gitignore` on the first build; 2.0.11 and 3.x share `~/.platformio/packages/framework-arduinoespressif32` (switching branches reinstalls the framework).
3. **Arduino-ESP32 2.0.11 → 2.0.17 (ESP-IDF 4.4.7, `espressif32 @ 6.11.0`): done in rc.9 (2026-11-22).** The last 2.x release; builds unchanged, same diagnostics on the V3 test node: 1–4 KB more free internal RAM (boot 247 → 256 KB, lowest 128 → 132 KB, largest block 123 → 127 KB). Tested: OTA-like app-only flash on the old bootloader, erased first start (portal), wireless reception, web pages (gzip and plain fallback), 2 h without restart. The measurements above were made on 2.0.11.
   - Reconsider when only V4 nodes (PSRAM) are left, or for a V4-only build.

- **The framework's `WebServer` has no request limits** (URI / header length, number of arguments, one request at a time, no login throttling). An oversized request can make the node restart; an uncaught allocation failure inside the library can't be caught from our code. Until then: keep the node in its own network (IoT VLAN), never reachable from the internet; public pages come from a separate project that pulls the REST API. Long-term: ESP-IDF's `esp_http_server` (see item 1 above: postponed).
