# Changelog

Release notes of the Universal Weather Node firmware, newest first. Binaries are in [`firmware/`](firmware/).

[← back to README](README.md)

## 4.0.0

Firmware: [`universal-weather-node-4.0.0.bin`](firmware/universal-weather-node-4.0.0.bin) (application only: updates of a 4.x node, USB at `0x10000`) and [`universal-weather-node-4.0.0-factory.bin`](firmware/universal-weather-node-4.0.0-factory.bin) (first installation, USB at `0x0`). For the **Heltec WiFi LoRa 32 V4** (V4.2 / V4.3, ESP32-S3R2) **only**; the V3 (legacy) stays with firmware 3.x, the V4-R8 is not supported.

**Updating**
- **From 2.x / 3.x:** not over the air. One USB installation of the `-factory.bin` with the web flasher (it erases settings and Wi-Fi): make a settings backup first, set the Wi-Fi in the config portal, restore the backup. Step by step: [Coming from 2.x or 3.x](docs/installation.md#coming-from-2x-or-3x). Chart history starts empty; the LoRaWAN session is not carried over. Trying the plain `.bin` over the air in an older 2.x ends with a message and a return to the 2.x firmware after 10 s; 3.0.0 and later (the successor of 2.0.5) refuse it.
- **From a 4.0.0 development build / later 4.x:** OTA with the `.bin` without `-factory`.
- **Logical sensors (★):** the ★ sensors are now a table of their own; **after the update from 2.x / 3.x or an earlier 4.0.0 development build it starts empty** — the ★ list, the names and minimum signals of ★ sensors, value sources set to a wireless sensor, the sensor of wireless alarm rules and wireless custom series are not carried over (also not from a 2.x / 3.x settings backup; everything else in it is). Mark your sensors ★ again and choose them again where they were used.

Not yet verified at release: a multi-day memory run, a real Prometheus server, virtual sensors with an Ecowitt gateway / console or a TFA / LaCrosse IT+ station, virtual sensors together with Davis reception, Davis wireless reception (experimental), Fine Offset reception on our own V4 (confirmed by a user on a V4.2), the V4 Full / V4 Light boards, several phones at once on the own access point.

**Heltec WiFi LoRa 32 V4 only** (ESP32-S3R2: 16 MB flash, 2 MB PSRAM). The Heltec V3 (and the PCB Rev 1.2 / 1.3) is legacy and stays with firmware **3.x** (branch `3.x`, bug fixes only). Tested on a Heltec V4.3 (KCT8103L front end): start and board detection, IT+ reception, the web server with login and login brake, all settings, backup / restore, firmware upload, config portal and setup wizard, both reset steps, crash report and core dump, the own access point with a phone (incl. the phone's time), MQTT with a real Home Assistant, InfluxDB 2.7, virtual sensors over the air (Fine Offset and IT+), and a real 3.x → 4.x migration with a backup restore.

**Coming from 2.x:** the partition table changed, so this is **one USB flash** of the `-factory` image — step by step in [Coming from 2.x or 3.x](docs/installation.md#coming-from-2x-or-3x). Over the air: 2.x refuses the `-factory.bin`, and 3.0.0 and later (the successor of 2.0.5) also the plain `.bin`; 2.x up to 2.0.5 accepts the plain `.bin` — 4.0.0 then shows a message and **goes back to the 2.x firmware by itself** after 10 s (a V3, a V4-R8, or a V4 that still has the 2.x partition table; tested on a V3 and on a V4 with the 2.x table). Make a settings backup in 2.x before (*Settings → System → Backup and restore*) and restore it afterwards; the chart history starts empty. A real migration with a backup restore is not yet tested end to end.

**Hardware and platform**

- **Framework: Arduino-ESP32 3.3.13 on ESP-IDF 5.5** (pioarduino) instead of 2.0.17 / 4.4.7 — the port from the 2.x experiment (pulse counters on the new `pulse_cnt` driver, LEDC, watchdog, Wi-Fi API).
- **16-MB partition table:** two 6-MB app slots (2.x: 3.2 MB), the settings partition `cfgdata` and the core dump as before, and a new 3.8-MB **`history`** partition — the saved chart history moved there from `cfgdata`.
- **V4 only:** no board setting and no V3 detection any more; on a V3 or a V4-R8 the firmware shows "Heltec V4 needed" on the display and in the log, does nothing else and restarts with the 2.x firmware if that is in the other OTA slot. PCB: only the V4 Full / V4 Light (revision ID on GPIO15); the PCB revision is shown, no longer set. The log always goes over the native USB.
- **Weather Node V4 Full Rev 1.0** (formerly **PCB v2.0**): the **Heltec V3 socket set J1/J2 was removed** — the board takes only a Heltec V4 (J19/J20 + P4 socket J21); the connections that ran through the V3 pads were re-routed, the silkscreen updated. V3 builds stay on the v2.0 files in the `2.x` branch. Files moved from `pcb/v2.0/` to [`pcb/v4-full/`](pcb/v4-full/) (`universal-weather-node-v4-full-*`), the case from `3dprint/v20-v4/` to [`3dprint/v4-full/`](3dprint/v4-full/) (`case_v4_full.py`); the V3 case `3dprint/v20/` was removed (in the `2.x` branch). Cases (D3): the V4 Full case gets an R-SMA knock-out for an optional Wi-Fi antenna (u.FL pigtail); the minimal wireless-build case is redrawn for the Heltec V4 (BME280 wiring on GPIO47/48, GNSS bay under the lid, LoRa SMA opening, R-SMA knock-out, separate louvred BME280 chamber) — not printed yet, GNSS module size still a placeholder.
- **New board: Weather Node V4 Light Rev 1.0** ([`pcb/v4-light/`](pcb/v4-light/README.md)) — through-hole, hand-solderable, 100 × 80 mm, Heltec V4 only, powered over the Heltec's USB-C: Davis wind / rain, switched vane supply, BME280, DS18B20 with switched supply; SMB TVS on the Davis lines, supplies and 3.3 V rail, optional low-capacitance PESD5V0S2BT at the I²C and 1-Wire terminals, plated mounting holes on GND, resistors on a 10.16 mm pitch (room for Vishay PR01), TVS diodes clear of the jacks and terminals, verbose silkscreen with part values on the front and the complete BOM, pinouts and assembly notes on the back. Not yet built or tested. Case: [`3dprint/case_v4_light.py`](3dprint/case_v4_light.py) (outline and connector positions from the KiCad board, cable bay with two M12 glands, LoRa SMA and an R-SMA knock-out; not printed yet).
- **Firmware detects the V4 Light:** revision ID on GPIO15 — 1.30–2.00 V = V4 Full (`pcbRev` 20, unchanged), **0.85–1.25 V = V4 Light (`pcbRev` 21)**, otherwise no PCB (wireless station, `pcbRev` 0). Detection is not yet tested on a built board. On the V4 Light the functions it does not have (heater, fan, tacho, AUX analog / pulse, UV, VE.Direct, second wind sensor) are hidden in the settings and refused by parameter except for switching off; status page and log name the board ("PCB V4 Full" / "PCB V4 Light"). See [Board detection](docs/pcb.md#inputs-and-outputs-v4-full).
- **Documentation:** "PCB v2.0" renamed to V4 Full throughout, V3 pin maps removed (they are in the `2.x` branch), [board overview](docs/pcb.md#which-board) and a V4 Light section added.
- **PSRAM used for more:** the device log keeps 64 KB (was 4 KB), the radio trace 256 KB (was 24 KB — about an hour with 20 sensors), up to 32 custom series (was 8 on a V4).
- **New web server** (ESP-IDF `esp_http_server` instead of the Arduino WebServer): several connections at once with keep-alive, request headers up to 2 KB and URLs up to 1 KB, an oversized or broken request is refused instead of disturbing the node, uploads are streamed. Login: several pages and requests at once without a new password prompt, after a restart of the node the browser logs in again by itself; wrong passwords are slowed down. TLS buffers in PSRAM.

**Features**

- **Logical sensors, step 1 (storage):** every ★ sensor is a *logical sensor* with an internal ID the node draws once (`L` + 6 hex digits), a custom ID (proposed: its radio ID), a name (*Bezeichnung*) and a minimum signal; the radio ID is only an attribute (re-bound after a battery change), stored as one table (NVS `lsens`). Value sources, alarm rules, custom series and the placeholders of OLED screens, custom uploads and alarm texts refer to the internal ID (placeholders are typed and shown with the custom ID, `{17000008_temp}`, and saved as `{@L3F9A2C_temp}`; the old `{rf<ID>_…}` / `{rfN_…}` still work). Only ★ sensors can be chosen there. The *Mine (IDs as text)* field and the portal field `rfids` are gone. Settings backup format **2** carries the table; a version-1 file restores everything except the ★ list and the references by radio ID. Sensor table (UI terms: *Funk-ID* / radio ID, *Interne ID* / internal ID, *Kennung* / custom ID, *Bezeichnung* / name, *Neu zuordnen* / re-bind, *Mindestsignal* / minimum signal): edit the **custom ID** (checked, unique), the radio ID and the internal ID are shown, **re-bind** after a battery change by a select of the received sensors of the same kind, and a *New sensor … replaces <name>?* button when a ★ sensor went silent and exactly one new sensor of its kind appeared. **Outputs on the custom ID (step 2b):** other systems now address a ★ sensor by its custom ID, a sensor that is only received as **`rf<radio ID>`** (`rf17000023` - that shape is refused as a custom ID, so the two can never collide) — MQTT topic `<prefix>/rf/<custom ID>` (payload with `customId`, `internalId`, `displayName`, `radioId`); Home Assistant `unique_id` / device `<node>_rf_<internal ID>…`, device name = the sensor's name (else *&lt;model&gt; &lt;custom ID&gt;*), state topic = the custom-ID topic — a new custom ID, name or re-bound radio ID re-announces the same entities (history stays), the old state topic is cleared; Loxone `<custom ID>_temp`, `<custom ID>_humidity` … (was `rfN_…`); InfluxDB tags `sensor=<custom ID>`, `radio_id`, `name` (if set); `/metrics` labels `sensor`, `radio_id`, `name` (was `id`); `/api/data` `rfSensors[]` keeps `id` (radio ID) and adds `customId`, `internalId`, `displayName`; `/api/alarms` adds `customId` next to `sensorId`; the alarm text `{sensor}` is the sensor's name (else its custom ID); dashboard card and status page show the name, else the custom ID. The table is guarded by a lock: the web server changes it while the radio, upload and MQTT paths read it. **Update note:** Loxone inputs `rfN_…` must be renamed once to `<custom ID>_…` (received-only sensors: `rf<radio ID>_…`); Home Assistant gets new devices once (the old per-radio-ID devices are removed at the first connection; the ★ list starts empty anyway); InfluxDB and Prometheus start new series (tag / label `sensor` instead of `id` — the custom ID, or `rf<radio ID>` for a sensor that is only received; group by `sensor`, not `name`); MQTT subscribers of `<prefix>/rf/<ID>` switch to the custom-ID topic (received-only sensors: `<prefix>/rf/rf<ID>`). Design: [docs/design/a5c-logical-sensors.md](docs/design/a5c-logical-sensors.md).
- **Minimum signal per wireless sensor (expert setting):** *Settings → Sensors* (advanced): a *Min. dBm* column in the sensor table and the text field *Minimum signal per sensor* (`ID:dBm|…`, field `rfminrssi`); weaker packets of that ID are dropped (not counted, shown as IGNORED in the radio trace) — hides a neighbour's twin sensor with the same ID. Default: none.
- **Auto search locks a weaker own sensor sooner:** the RSSI threshold starts at −85 dBm and falls by 15 dB over the 30-min search (e.g. a −90 dBm sensor locks after about 10 min instead of 30); 3 packets in 10 min are still needed, of several the strongest wins.
- **IT+ sensors with the same ID kept apart:** IT+ has only 64 IDs, so a neighbour's sensor may share yours — its values then landed in your sensor (seen on the test node: 10 °C / 98 % from a humidity sensor under the ID of a temperature-only one, which also set the day's maximum). A sensor **with humidity** now gets `1` in the third-last digit of its ID (`170001xx` / `090001xx`), so a temperature-only and a temperature/humidity sensor stay two rows; the table marks both *ID shared* (`/api/data`: `idTwin`). **Update note:** an IT+ sensor with humidity changes its ID from `170000xx` to `170001xx` — select it again as value source / ★ (from 2.x the backup carries the old ID).
- **Chart history saved every 30 min** (own `history` partition): a power cut or a crash loses at most 30 min (2.x: the hourly values once a day, the 5-min values only before a planned restart).
- **Long history (node side of B2):** the hourly values now reach back **35 days** (was 7) and a new **daily tier keeps 2 years** of local calendar days (mean, gust maximum, rain total, **minimum / maximum of temperature, humidity and pressure** — new for every tier, `tempMin` / `tempMax`, `humMin` / `humMax`, `pressMin` / `pressMax` in `/api/history`, in the units of their means). A day is built from its hours and closes at local midnight (23 / 25 h at the DST changes), so its rain and extremes match *rain today* and the records; after a restart the current day is rebuilt from the saved hours and the current hour from the saved 5-min values (weighted by their number of cycles, so the hour comes out as without the restart). `/api/history` gets `range=30d` (2-h points) and `range=1y` (days), `end=<unix seconds>` for an earlier window (period compare: this week vs last week, this year vs last year) and `res=5m|1h|1d` to force a tier; long ranges are downsampled on the node to at most 400 points; the response names `range`, `res` and `bucketSec`, `/api/info` lists the ranges and the tiers. Custom series get the long tiers too. Memory: 80 KB of PSRAM for the rings (44 bytes per bucket; +3.6 KB per custom series), the open buckets in the PSRAM too; the `/api/history` document is built in the PSRAM. Each tier is saved only when it has changed (5-min values every 30 min, hourly once an hour, days once a day; at most ~3.8 MB of flash writes a day with 32 custom series, 1.5 MB without — each page of the 3.8-MB partition erased about once a day, centuries of flash life). **Update note:** the chart history saved by an earlier 4.0.0 development build is in the old format and is dropped once (the charts start empty).
- **Dashboard: long history (B2 UI):** range buttons 24 h / 7 d / 30 d / 1 year, *Earlier / Later / Now* and swipe to pan through the history, *Compare with previous period* (dashed line, lighter rain bars), min/max band for temperature, humidity and pressure for 7 d and longer, calendar x axis; past windows are fetched once. See [Web dashboard](docs/web-dashboard.md).
- **Prometheus endpoint `GET /metrics`** (no login, CORS like `/api/data`): the selected weather values and every wireless sensor (labels `sensor` — a ★ sensor's custom ID, else `rf<radio ID>` — `radio_id`, `model`, `name`, `channel`) plus system values (uptime, heap, Wi-Fi RSSI) in Prometheus text format, in fixed SI base units (Celsius, m/s, hPa, mm, lux) regardless of the display units; a sensor that has gone silent shows `uwn_rf_up 0` and its `uwn_rf_age_seconds`, without measured values — format checked with a strict exposition-format checker (0 errors); **not yet run against a real Prometheus server**. Scrape it with Prometheus, VictoriaMetrics, Grafana Alloy or Telegraf, no MQTT detour. The node stores no database credentials and opens no connection.
- **InfluxDB / VictoriaMetrics push** (*Settings → Outputs*): the node pushes the same values as line protocol to a configurable write URL on its own interval, with the timestamp in the packet (olicat, forum #62) so late data is accepted; wireless sensors as `<measurement>_rf` with the tags `sensor` (custom ID / `rf<radio ID>`), `radio_id`, `host`, `model`, `name`, `channel`. Works with InfluxDB v1 (`/write?db=`), v2 (`/api/v2/write?org=&bucket=`, token: a bare token is sent as `Token …`) and VictoriaMetrics (no auth); plain HTTP or unverified TLS by the URL scheme. A wireless sensor that has gone silent is left out (its old values would get the current timestamp). Off by default. Checked against VictoriaMetrics 1.157; **not yet against a real InfluxDB**. **Backfill after an outage:** every push goes through a 512 KB queue in the PSRAM; while the database or the network is unreachable (no Wi-Fi, no reply, HTTP 5xx, 401 / 403 / 404 / 408 / 429) the pushes are kept and retried (30 s, doubling up to 10 min), then sent oldest first in requests of up to 8 KB with their original timestamps; a push the database refuses (other 4xx) is dropped with a log line; a full queue drops the oldest push (~8 h at 60 s with a few wireless sensors). RAM only — a restart or power cut loses the backlog. Backlog size, oldest age and dropped counts on the status page and in `/api/info` (`outputs.status.influxdb.backlog`, new `outputs.influxdb`); the push has a send-status entry like the other outputs.
- **Network sensors** (*Settings → Sensors → Network sensors*, advanced; [docs/network-sensors.md](docs/network-sensors.md)): up to 4 sensors whose values come over the network — an **MQTT** topic on the node's broker (JSON with a key per value, or a plain number per topic) or a **REST** URL polled every 30–3600 s (http / https, in the upload task, TLS gate) — enter the sensor table as IDs `E1000001`–`E1000004` and are used like a wireless sensor: value sources, ★ (set when switched on), custom ID, history, dashboard, `/api/data`, MQTT out, Home Assistant, weather networks, LoRaWAN, virtual sensors. Preset **Universal Weather Node**: the `<prefix>/data` (MQTT) or `/api/data` (REST) of another node of this firmware with its units converted — only the topic / URL is entered. Keys as dotted paths (`main.temp`, `list.0.temp`); only the mapped keys are kept while parsing. Labelled **MQTT / REST** instead of a radio protocol everywhere (status page, settings table, value-source select, dashboard, `rfSensors[].protocol`); per-sensor freshness window (default 10 min) after which the values are stale, so a dropped VPN / broker never keeps an old value as current. Status page: messages, last one, last error (HTTP code, invalid JSON, no mapped value). With 868 MHz reception off, network sensors alone keep the sensor table in use. **Device test open.**
- **Virtual sensors** (*Settings → Outputs → Virtual sensors*, advanced; [docs/virtual-sensors.md](docs/virtual-sensors.md)): the node sends its own values as Ecowitt / Fine Offset sensor frames on 868.3 MHz (17.241 kbit/s FSK, sync `2D D4`), so a gateway or console shows e.g. a wired Davis as a **WH65**, a BME280 as a **WN32P**, any temperature as a **WH31** (channel 1–8) or a rain total as a **WH40**. Up to 4 sensors, every frame field mapped freely to a station value (main and derived values, ★ sensors, DS18B20 probes, `rain_total`); intervals of the originals (16–64 s) with jitter; transmit power 0–14 dBm (default 10) with the V4 front end's gain taken into account. Sent between the receive phases, never during a LoRaWAN uplink; the node's airtime in the 1 % band (virtual sensors + LoRaWAN) is counted per hour and a frame beyond 36 s/h is skipped. **Red line, enforced by the code's structure and tests:** only readings from the typed encoders (no raw-byte path anywhere), no actuator / gateway / command frames, the ID is derived from the node's MAC (not configurable; never a foreign ID, no repeater), off by default. Status page and `/api/info` (`virtualSensors`): frames sent, last frame, skipped (airtime / radio busy / value missing). A warning shows when a received sensor has the same ID (WH31 IDs have 8 bits; the ID stays stable). **Received by a 2.0.5 node set to Fine Offset** (WH31 and WN32P frames decoded with the mapped values); **not yet tested with an Ecowitt gateway / console**.
- **Live values on the display** (V4): the OLED and the custom screens now show temperature, humidity, pressure, UV and light **per received packet** (like the wind already did), instead of only once per measurement cycle — so the screen catches up the moment a sensor is heard. Uploads, alarms, history, LoRaWAN / MQTT / weather networks and the API keep using the cycle snapshot, and derived values (dew point, feels-like, pressure tendency, rain, records) stay on the cycle; the screen may briefly show a newer value than the last logged one, which is intended. Done by sharing the source selection between the cycle and a side-effect-free live read (`srcLive()`), so both always pick the same source. (Not yet checked on the OLED itself.)
- **Status LED** (*Settings → Display*, formerly *Heartbeat LED*): besides the heartbeat (2 s) the white LED can flash for every valid packet of your ★ sensors or of every sensor — you see at the node that the sensors arrive. Existing settings are kept.
- **Screensaver** (*Settings → Display*, V4): every 1–60 min (default 5) the OLED is taken over for 3–30 s (default 8) so the always-lit pixels rest — **brief blank**, **moving dot**, **weather icons** (sun, cloud, rain) or a **walking figure** that reacts to the current values (frost, thaw, mild, hot, UV, rain, wind, lightning, fog, bad air, dry soil, night) with a pool of small animations and rare surprises. Off by default; only while the display is on and not in the night hours; a PRG press ends it. Preview button on the settings page.
- **Time sources and LoRaWAN network time:** the clock now follows the best fresh source in a fixed order — GNSS (reserved) > **NTP** (24 h fresh) > **DCF77 radio-clock sensor** (WH31 / WN31 DNT, 25 h; used once two consecutive frames agree, not in the repeated DST hour) > phone (reserved) > **LoRaWAN `DeviceTimeReq`** (24 h); a worse source never overrides a fresh better one. A LoRaWAN-only node asks the network for the time with the first uplink after each join and then daily (every 6 h in low-power mode; none while NTP is fresh), so it has "today", records and the daily history without Wi-Fi. NTP answers go through the same rules (lwIP's `sntp_sync_time` replaced). The time zone now also applies without Wi-Fi (before, only NTP set it). A clock that steps **back** no longer breaks the history (no window or day twice: the open bucket lasts until the clock has passed it) nor "today" in the records, rain statistics and per-sensor rain (a step back over midnight stays on the day). Status page: *Clock* (source, age, "running on its own" when stale) and *LoRaWAN → Network time* (last answer, next request); `/api/info` `measurement.clockSource`, `clockSourceAgeSec`, `clockSourceFresh`, `loraTimeReqInSec`. **Not yet tested against a real network server** (ChirpStack / TTN). See [LoRaWAN → Time](docs/lorawan.md#time-sources-and-network-time-devicetimereq).
- **Own Wi-Fi access point (B8)** for places without Wi-Fi, e.g. a model airfield (*Settings → System → Own access point*, live): **off** / **fallback** (opens when the Wi-Fi network has been unreachable for 2 min, keeps trying it every 2 min, closes once it has been back for 1 min) / **always** (alongside a stored Wi-Fi network, or access point only). Own SSID (default `WeatherNode-<MAC>`), WPA2 password (8–63 characters, required — never an open network), channel (auto = the station's). 192.168.4.1/24 with DHCP (8 devices), a **captive DNS** answering every name with the node, the RFC 8910 captive-portal URI in the DHCP offer, mDNS as before. Phones' connectivity checks (Android, Apple, Windows, Firefox) and foreign host names get a redirect to the dashboard — the phone opens it in its sign-in sheet and keeps using mobile data for everything else; only for devices on the access point, the station LAN is unchanged. The **dashboard sends the browser time** (`POST /api/time`), taken as the time source *phone* over the access point or while the node has no fresh time. A **WiFi QR code** screen on the OLED (on by default, shown only while the access point runs, first when the display comes on) and the QR code on the status page; own QR encoder (versions 1–10, checked with Apple's Vision decoder). Status page *Access point*, `/api/info` `outputs.accessPoint`, `accessPointActive`, `accessPointClients`. How-to: [At the Airfield](docs/airfield.md). **Not yet tested on the V4 with real phones.**
- **GNSS module (B9)** on a Heltec V4 **without** PCB (*Settings → Sensors → GNSS module*, off by default; never offered on the V4 Full / V4 Light, which use the pins): Heltec's module (UC6580 / L76K) on the V4's GNSS connector — supply GPIO34, UART1 RX 38 / TX 39, wake 40, PPS 41, reset 42 (from Meshtastic's V4 variant; supply polarity and RX / TX still to be confirmed on a real module), 9600 / 115200 / 38400 baud found automatically. Own NMEA reader (RMC, GGA, ZDA, any talker, checksum checked, bounded line buffer, read in the main loop). **Time:** source `gnss`, the best one (before NTP, DCF77 sensor, phone, LoRaWAN), taken only with a fix (RMC status *A*), timestamped by the PPS edge (~20 ms) or, without PPS, by the line (~1 s). **Position / altitude** (each switchable): the mean of 5 min of good fixes (≥ 4 satellites, HDOP ≤ 2) goes into latitude / longitude when it moved > 100 m and into the station altitude (sea-level pressure) when it differs by > 5 m — no flash write per wander. Status page (fix, satellites, HDOP, position, altitude, last GNSS time, PPS), `/api/info` `hardware.gnss`. **BME280 of the wireless build moved to GPIO47/48** (own I²C bus, the S3's second controller; 41/42 belong to the GNSS connector), address 0x76 or 0x77. **Update note:** a BME280 still wired to 41/42 (as documented for 2.x) keeps working while GNSS is off — status page and log say *"BME280 on the old pins 41/42 — works; move it to 47/48 for a GNSS module"*; with GNSS on, 41/42 are never used for I²C. `/api/info` `hardware.bme280Pins`, `bme280OldPins`. With a PCB the BME280 stays on 41/42. Docs: [Minimal build](docs/minimal-build.md#gnss-module-optional), [Settings → GNSS module](docs/settings.md#gnss-module). **Not yet tested with a real module.**
- **New sensor — LDS01:** the Fine Offset laser distance sensor is now decoded — the distance (air gap) in mm and the heater-on count — and shown on the status page, in `/api/data` + MQTT, `/metrics`, the InfluxDB push, Home Assistant (distance / heater-on-count entities) and the history charts (chartable level); the radio trace prints the values instead of "values not decoded yet" (confirmed against the console readings in Dirk's trace — thanks).
- **Dashboard: sparklines on the tiles (B3):** every value tile shows the last 24 h as an inline SVG line from the already loaded history (theme-aware, hidden without data, no layout jump).
- **Dashboard: page per wireless sensor (B3):** `#sensor=<custom ID or radio ID>` shows IDs, model, values, signal, age, battery and the history charts of the value groups the sensor supplies; opened from the sensor list or the tiles. No new data on the node.
- **Dashboard: CSV export (B3):** the button *Export CSV* saves the shown history window as `uwn-<host>-<range>-<date>.csv`, built in the browser (local ISO time, UTC epoch, one column per series with unit).
- **Dashboard: live badge, flash on change, age of values:** next to *Updated* a green badge **● Live** shows that the values arrive directly through the event stream (tooltip explains it); when the stream is not available (node already serving 3 dashboards, error) a grey badge shows the polling interval (*every 30 s*); nothing with auto-refresh Off. Two new node settings in *Settings → System → Web UI* (both off by default, read by the dashboard from `/api/info` → `ui`): **Flash tiles on change** (a tile highlights for 1 s when its value changes; not with reduced motion) and **Show age of values** ("3 s ago" per tile, counting up; from the wireless sensor's last packet, else the last measurement cycle).
- **LDS01 on the dashboard:** the sensor card now shows the distance in mm.
- **Radio trace:** while a capture runs, unknown Fine Offset-band frames are recorded with up to 64 bytes instead of 32 (e.g. Ecowitt IoT devices).
- **Radio trace:** the *one sensor ID* filter also matches a short ID (e.g. `2801` or `802801` for a sensor shown as `54802801`), so a targeted capture no longer stays empty when only the lower part of the ID was entered.
- **Custom series extended (C3):** **32 series** (was 16); per series a selectable **aggregation** — mean, minimum, maximum or sum (default per value as before: lightning strikes sum, storm distance minimum, else mean) — used alike for the 5-min, hourly and daily buckets and the downsampled points of long ranges. The series are now also **outputs**: placeholder **`{series_<slot>}`** (custom uploads, alarm texts, OLED screens; temperatures with `:c` / `:f`, pressure with `:hpa` / `:inhg`; `series` can therefore no longer be a custom ID), `/api/data` and the MQTT data topic `series[]` (`slot`, `name`, `sensor`, `field`, `agg`, `unit`, `decimals`, `value` = the last cycle's), **Home Assistant** one sensor per series (object id / `unique_id` `<node>_series_<slot>`, unit and device class from the value; a freed slot is removed; re-announced after saving the series), InfluxDB field `series_<slot>` on the main line, `/metrics` `uwn_series{slot,name,field,unit}`. Settings page: one collapsible block per slot (defined ones open, the free ones closed), the placeholder in its title. The definitions left `Config` for their own PSRAM store (32 × 34 B; NVS string `series` as before), so settings copies stay small. Memory: rings 3.6 KB of PSRAM per series (116 KB for 32); flash: at most ~3.8 MB of history writes a day with 32 series (see *Long history*). `/api/history` `series[]`: the value key is now **`field`** (was `value`), new `agg`. **Fix:** a downsampled point of a custom series (30-day / 1-year range) took the previous point's value instead of its first bucket. **Update note:** none — stored series of an earlier development build are read as they are (the default aggregation keeps their history).
- **Reception watchdog for ★ sensors (B10):** every ★ radio sensor's packets of the last hour are compared with the packets expected from its learned send interval (the timed reception's). Status page and dashboard show *reception NN %*, below **30 % over a full hour** a warning *reception poor* — a reception problem (antenna, position, obstacle) while the sensor still sends, distinct from a *silent* sensor (stale, battery). Unknown until an interval is learned and 10 min of data are there; a ★ / re-bind (battery change) or an hour of silence starts a fresh hour; repeats count once. Outputs: `rfSensors[].reception` (%, `null` = unknown) and `receptionPoor` in `/api/data` and the MQTT sensor topic, Home Assistant diagnostic entity *Reception* (`<node>_rf_<internal ID>_reception`), alarm value *reception (%)* of a wireless-sensor rule (`receptionPct`). Nothing allocated in the radio path. **Two sensors on one radio ID** (IT+ has only 64 IDs): packets closer than 0.75 × the type's fixed interval (IT+ about 4 s; Fine Offset sensors with a fixed interval), or closer "repeats" with other values, can only come from a second transmitter — at least 5 within the hour and at least 20 % of the packets show *⚠ two sensors are sending with this ID — values are mixed* with the fix (re-insert the battery, re-bind), `rfSensors[].idCollision`, HA attribute `id_collision` on *Reception*; reception reads unknown meanwhile, the warning ends after an hour without such a gap. The interval learning no longer drops to half the interval in that case (it ignores gaps below 0.75 × the fixed interval). Memory: 28 bytes per table entry (7 ten-minute counters each for packets and impossible gaps, 896 B internal RAM in all; was 20). Docs: [Reception watchdog](docs/wireless-sensors.md#reception-watchdog). **Not yet tested on the V4** (detuned antenna / shielded node; the twin warning with the neighbour's IT+ sensor).
- **Crash report and reset history (B11):** the node keeps why it restarted the last 10 times — cause (power-on, reset button, software restart *with its reason*, crash, task / interrupt watchdog, brownout, USB), how long it had run before and when (a heartbeat in RTC RAM, refreshed once a second). After a crash it reads the ESP-IDF **core dump** the panic handler left in flash: task, address, backtrace, the panic details (an assert names file, line and function; the task watchdog names the hung tasks) or the CPU exception. Shown on the status page (*Last restart*, *Restarts before*, *Last crash*) and in `/api/info` (`system.resets`, `system.starts`, `system.lastCrash`); the whole dump is an **admin download** (Settings → System → Diagnostics, `GET /api/diag/coredump`; it holds the RAM contents — keep it private), decoded with the build's `firmware.elf`. A **test crash** (panic, or a hang until the watchdog) is behind the login, a same-origin request and the typed word `CRASH`. Docs: [Crash report](docs/design/storage-layout.md#crash-report).
- **Task watchdog over every network task (B11):** besides the main loop, the web task, the upload task (weather networks, notifications, InfluxDB …) and the web server's request handlers (while one runs, fed as long as data moves) are watched — a hang there resets the node after 120 s and leaves a core dump, instead of a web interface or uploads that stay dead.
- **Virtual IT+ sensors (TX29 / TX35 style):** two new virtual-sensor types send a LaCrosse / TFA IT+ temperature (+ humidity) frame at 17.241 kbit/s (every 15 s) or 9.579 kbit/s (every 22 s) for an IT+ station — 6-bit ID derived from the node, new-battery flag for 5 min after switching a slot on (pairing), collision warning for a received IT+ sensor with the same ID; 8 IT+ slots fit the airtime plan. Deviation unmeasured; **not yet tested with an IT+ station** ([docs/virtual-sensors.md](docs/virtual-sensors.md#it-tx29--tx35-style)).
- **Virtual sensors in Davis mode (C5):** they used to be skipped (*radio busy*) while Davis reception owned the radio; now the Davis receiver sends up to 2 waiting frames in the gap right after each Davis packet that matched the hop prediction and is back on the next hop channel ≥ 300 ms before the next packet can start. Never after a missed packet or while searching; a frame that found no gap before its sensor's next one counts as *deferred (Davis)* (status page, `/api/info` `skipped.deferredDavis`); *Davis gaps* shows the frames sent and the longest gap use measured (`davisGapFrames`, `davisGapMaxMs`). Airtime budget unchanged (1 %). Not yet tested with a real Davis transmitter.
- **8 virtual sensors** (was 4) — e.g. a WH31 on each of the 8 channels a gateway knows (8 × WH31 plan 4.3 s of the 36 s airtime per hour; at most 5 WH65). Their settings moved out of the configuration into their own store in the PSRAM with their own versioned NVS blob — internal RAM does not grow.
- **Storage layout frozen for 4.0.0 (B11):** partition table reviewed once — settings partition `cfgdata` 64 → 128 KB, `coredump` 64 → 128 KB, `history` 3.8 → 1.5 MB (it needs at most 201 KB), and a reserved 2.2-MB `files` partition for a later file system; app slots stay 6 MB. Every stored format carries a version, and later firmware converts older ones in one place ([Storage layout](docs/design/storage-layout.md)). **A node on a 4.0.0 development build needs one USB flash of the `-factory` image (erases the settings — back them up first).**
- **HTTPS with your own certificate (C4, optional):** *Settings → System → HTTPS* — paste a PEM certificate (chain) and its private key, tick *HTTPS on port 443*; the web interface and the API then also answer on `https://`. HTTP stays the default; port 80 either **stays available** or **redirects** (`307`, temporary on purpose, no HSTS) — never for devices on the own access point; the setup portal stays plain HTTP. Before a pair is stored it is checked: complete PEM blocks, no private key in the certificate field, no password-protected key, then mbedTLS (both parse, the key belongs to the certificate) — a failure names the reason and keeps the stored pair. The key is write-only (never shown, in a backup only with *include passwords and keys*), stored in NVS (`config`/`https`, versioned; a factory reset deletes it). **Never locked out:** if HTTPS cannot start (no pair, unusable pair, too little memory, server start failed) the node runs plain HTTP without redirect and the status page / `/api/info` `outputs.https` say why. Built on `esp_https_server` as a second listener on the same routes (requests of both handled one at a time). Memory, measured on the V4: ~21 KB internal RAM while HTTPS runs (106 → 85 KB free), per open HTTPS connection ~2.4 KB internal + ~37 KB PSRAM; at most 5 HTTPS connections, 2 of them live streams (SSE); handshake ~0.4 s with EC P-256. `LWIP_MAX_SOCKETS` 16 → 20 (two servers). The docs also show a small own CA with OpenSSL: [HTTPS](docs/settings.md#https). Tested on the V4 with a test certificate built in (curl with CA verification, 30 parallel requests over both ports, SSE limit); **the settings path behind the admin login (upload, save, restart) is not yet tested on the device.**
- **HTTPS without your own certificate, "HTTPS only" (C4b):** enable HTTPS without uploading a pair (or with one that is not usable) and the node **generates a self-signed certificate** — EC P-256, CN "Universal Weather Node <device name>" / O "Universal Weather Node" (trust stores list it by that name), SAN `<hostname>.local` + the current Wi-Fi address, 825 days (Apple's limit), random serial, marked as its own CA (Android / iOS trust only CA certificates) with *serverAuth*. Stored next to the uploaded pair (`config`/`httpsgen`, same versioned format; never over the uploaded one, never in a backup, cleared by both resets) and reused at every start while it still names the host name, the address and the current device name and has not expired, else made anew. It waits for the station address (with only the own access point up HTTPS starts once Wi-Fi connects); an address that changes later shows on the status line, *Generate new certificate* fixes it (restarts only the web server). *Settings → System → HTTPS* shows the active certificate (generated / uploaded, CN, names, end date), **Download certificate** (`GET /api/https/certificate`, public, never the key) and the trust steps for Windows / macOS / Android / iOS / Firefox are in the [docs](docs/settings.md#generated-certificate); until trusted, browsers warn and Chrome registers no service worker. Port 80 now has three levels: **stays available**, **redirects browser pages** (a `GET` accepting `text/html`; API, scripts, posts and uploads stay on http — was: everything redirected) and **HTTPS only** (every request, the API and firmware upload included); never for the own access point, and while HTTPS does not run port 80 serves everything. `/api/info` `outputs.https`: `noCert` / `badCert` replaced by `waitingForNetwork` / `generateFailed`, new `outputs.httpsCertificate`. Measured on the V4: generation 233–237 ms, ~1 KB PSRAM, internal RAM unchanged, ~5.8 KB peak of the web task's 8 KB stack (2.4 KB left); HTTPS running with the generated certificate ~22 KB internal RAM as before; firmware +20 KB. Tested on the V4 with HTTPS forced on by a temporary build: generation, reuse after a restart, a new certificate at runtime, `curl --cacert` by name and by IP, the three port-80 levels (page / API / upload), `openssl` shows the SANs; **the settings path behind the admin login is not yet tested on the device.**
- **More internal RAM (B12):** every JSON document of the firmware (`/api/data`, `/api/info`, SSE, MQTT, backup, uploads …) is now built in the PSRAM, the status page's output-status copies are shared, and the 64-KB log lives in the PSRAM from the first line (no static 4-KB boot ring). V4, same load (3 event streams + data / 7-day history / dashboard requests): static RAM 112.9 → 105.4 KB, free heap settled 106.5 → 115.2 KB, lowest free under load 92.9 → 105.3 KB, largest free block under load 47.1 → 63.5 KB; after the load the free heap returns to its settled value (before: 7 KB stayed in the static JSON documents).
- **Reset in two steps (B13):** *Settings → System → Reset* — **Reset settings** (type `RESET`; also downlink `0xFF` and MQTT `factoryReset`): every setting back to its default, but Wi-Fi, static IP, device name, own access point, admin password, language and the LoRaWAN keys stay, so the node comes back at its address; records, rain statistics, chart history, restart history and core dump stay too. Unlike the old factory reset it also clears the alarm rules **and channels** (tokens) and the custom uploads. **Erase everything — hand the device on** (type `ERASE`, web only): erases the settings partition, the chart history, the core dump and the stock `nvs` partition (Wi-Fi credentials, LoRaWAN session) and the rain totals in RTC RAM; the node starts like a new one with the setup portal. Both seal the storage first: a settings save or a store flush racing the reset can no longer bring old data back. `POST /api/system/reset`. Details: [Reset](docs/settings.md#reset).
- **Storage review (B13):** a restore drops every field the page does not have (it stopped after 96); the ★ sensor table of a restore is only swapped in when the settings POST runs (a refused restore changes nothing); the own access point's password is only in backups *with passwords and keys*; custom series definitions are copied under a lock (a torn copy could pair one sensor with another's value); the six weather-network intervals and the altitude are clamped on load like the other settings; after a downgrade the reset history, chart history and records of a newer firmware are kept untouched (the older one keeps its values in RAM until the user deletes that store) — the rain statistics are the documented exception; stored blobs larger than today's format still reach the migration hook (a format may shrink later); the crash-dump firmware check compares exactly the SHA digits both sides hold.
- **Web server review (B13):** a request's body is bounded before any handler or login check runs: at most 2048 form fields and 128 KB of field data (one buffer, PSRAM when large), multipart bodies 128 KB unless the route takes an upload, 30 s per body (5 min for an upload) — a flood such as 128 KB of `a&a&…` or thousands of multipart fields from any LAN client used to be able to exhaust the memory and reset the node; it now gets `413`. Digest login: every nonce count is accepted once (a recorded admin request can no longer be replayed within the hour), the brake on wrong passwords is per client address and answers `429` with `Retry-After` instead of sleeping 1 s with the server lock held (which also slowed requests without any login and everyone else), and protected URLs up to the server's 1 KB limit can log in. A firmware upload only becomes the boot image once the whole request was received (a connection lost after the file part, or a second file part, no longer leaves a new firmware to boot at the next restart). Setup wizard step 2: ★ / ✕ on the **first** sensor row work (a nested form posted the wizard instead). The settings page and the wizard no longer hold the weather-network / Loxone locks while sending to a slow browser. After a save that needs a restart no other save (★ button, downlink, MQTT command) can put the old values back (further saves wait for the restart; the settings page says so); the wizard keeps a downlink change made while it saves. An alarm message or all-clear that does not fit is refused and keeps its old text (it was stored cut). `/api/info` → `hardware.gnss.lat` / `lon` only with the admin login. Smaller: `nan` as a coordinate, `12abc` in number fields, an update URL not starting with `http://` / `https://` are refused (the URL can now be emptied), `webadminpw_clear` cannot empty the admin password, a partial POST keeps a custom screen's layout, multipart `name=` without a space is read, freed request bodies and HTTPS key buffers are zeroed.
- **Outputs review (B13):** **CWOP** uploads no longer always report *FAILED* (the login answer was read with a 5 ms timeout on the new framework; now 5 s, and the first line with `logresp` counts); the MQTT connect timeout is really 3 s for TLS too. **MQTT:** only the main loop touches the MQTT connection (the status page read the TLS connection from the web task — sporadic disconnects, worst case a crash); a **retained** message on `<prefix>/cmd` is ignored (a retained `restart` caused a restart loop), nothing runs while *MQTT commands* is off, a `params` entry without `value` is refused; a broker that drops the session within 60 s (e.g. two nodes with the same name) no longer causes a reconnect storm; security *verified* without a CA certificate does not connect (status *verified TLS: no CA certificate*) instead of silently not verifying. **Home Assistant:** entities of a switched-off function are removed; numeric entities have a state class (long-term statistics; sums `total_increasing`), wind speeds `wind_speed`, the rain rate `precipitation_intensity`; DS18B20, sun / moon, wind 2, heater / fan, Victron templates no longer log errors while their object is missing; network sensors get no *Signal Strength* / *Battery* entity. **Network sensors:** a JSON / REST / preset message without a gust or direction no longer reuses an earlier message's (plain topics keep it, as documented); `+` / `#` refused in plain-topic keys. **InfluxDB / `/metrics`:** `rain_total` / `uwn_rain_total_mm` is the running total since the start (it was the last cycle's amount); URL / token are read under the settings lock. **Alarms:** minimum duration and repeat work past 49.7 days uptime (a pending rule raised at once, repeats fired at once); a message dropped from a full queue while another was being sent no longer passes its channels to the next one or swallows it; the MQTT alarm topics are published without holding the alarm lock; `{message}` and other text placeholders are no longer cut at 95 characters; a webhook / custom upload whose URL or body does not fit is not sent (status *too long, not sent*) instead of sent cut. **Weather networks:** an unknown wind direction is left out instead of sent as 0° (north); replies are read only as far as needed (a large error page no longer fills the memory); the update check no longer reads an error object as *up to date*. Smaller: per-sensor rain / lightning statistics and today's records are no longer written by the web task; the Loxone host lookup runs under the lwIP lock.
- **Time + GNSS review (B13b):** with a GNSS PPS pulse, a time sentence read after the next second's pulse (9600 baud, long sentence burst) is no longer stamped with that pulse — the clock could be set 1 s off while claiming 20 ms; it now falls back to the 1-s sentence time. Switching *Take the time* off hands the clock to NTP / DCF77 / phone at once (it waited up to 1 h). The GNSS position mean works across the antimeridian (±180°: it averaged to 0° and could write a position 19 000 km away), and the GNSS status no longer shows the last position / altitude as valid after the fix is lost. LoRaWAN network time stays fresh for 26 h, so the clock no longer shows *running on its own* every day before the daily request is answered. Per-sensor rain / lightning hours no longer reset every 49.7 days on a node without a clock. Smaller: a ZDA sentence with an out-of-range date field is refused safely; local times on the status page, custom uploads and radio-trace file names are formatted under the time-zone lock; sun elevation / sunshine by radiation use the cached day's location (no torn coordinate while GNSS takes a new one over).
- **Board / sensors review (B13b):** the 10-min wind of a wireless wind sensor really covers 10 minutes — it held the last 80 packets, only ~3.4 min with a Davis ISS (2.56 s) and ~6 min with a WS80, so weather networks and the *10 min* LoRaWAN / MQTT setting got a shorter mean and gust; it is now kept in 15-s time buckets (less RAM, independent of the packet rate). The fan's *minimum PV power* condition has a release band (off only below the limit minus 10 %, at least 1 W), so PV power around the limit no longer switches the fan every second. The 2nd anemometer sends no value for a cycle without an accepted sample (it repeated the previous cycle's). The daily-rain records include the last cycle of the day. Smaller: a non-finite pressure change gives no tendency instead of *rising very rapidly*; value sources are resolved with one copy of the ★ list per pass instead of a heap allocation per lookup; corrected texts (BME280 on GPIO47/48 without a PCB).
- **Dashboard review (B13b):** *Today* min / max / peak gust and a wireless sensor's rain *today* / *last hour* follow the *Units* button (they kept the device's unit under the other unit's label), and the hero card's *Today ↓ ↑* shows the node's true extremes instead of bucket means. A node without a clock is detected: *Earlier* and *Compare* are disabled with a note (the node would have answered the current window), and the page offers the browser's time again once a minute while the clock is unset (it did so only once per page load). Custom series for pressure, voltage and CO2 auto-scale instead of starting at 0. The page works with browser storage blocked (it stayed on *Loading...*). The offline service-worker cache keeps one history entry per range and ignores past windows. No overlapping polls, no polling in a hidden tab (also the log page), records at most once a minute and the history at most once a minute while live events flow; unchanged data with wireless sensors no longer redraws every second. Smaller: the calibration *Capture* button is locked while the request runs and a reply without an ADC value is an error; the autumn DST hour no longer merges two rain bars; sun / moon times and record tooltips use the page language; the help page keeps code spans literal and escapes quotes; the trend charts have an accessible name.
- **Display review (B13b):** a short PRG press while the display is on shows the next screen (as documented; it only restarted the timeout), and a long press now needs a press the node has seen held for 3 s — a bounced or lost button edge could reuse an older press time and open the config portal (and restart the node) on a short tap. In *always on* mode a press no longer makes the display blink off and jump to the first screen 20 s later. Shorter French / Spanish / Portuguese display texts that were cut off (*pas de données*, the storm warning on the pressure screen). The classic screen shows humidity only when its source has a fresh value (a temperature-only wireless sensor showed 0 %rH). The Wi-Fi QR code also works with a 32-character network name and a 63-character password full of characters that need escaping (the screen showed *Wi-Fi AP off*). Smaller: uplink result lines no longer flash over the screensaver, the restored screen keeps its full rotation time, the *thaw* figure no longer comes back 49.7 days after a frost, the screensaver preview shares no state with the display, the battery overlay no longer hides the end of the network name on the QR screen, network name / password on the QR screen are cut by their drawn width, custom-screen fields drop invalid UTF-8 bytes; docs: custom-screen lines hold 63 bytes.
- **Infrastructure review (B13b):** a full alarm queue (ntfy / Pushover unreachable) no longer drops a pending notification for an alarm that only reports over MQTT. Before the setup is done and while no admin password is set, a wizard step without login can only change the fields of that step (it could send the whole settings form). *Reset settings* clears only once every save still writing has finished, so no old key can come back next to the kept ones; an *Erase everything* already requested is no longer turned into a *Reset settings* by a downlink or MQTT command within the same second; and with too little memory the reset answers with an error instead of saying *started* and doing nothing. A wizard step and a downlink changing the same setting at the same moment no longer mix the two values into a third one. Log lines from different tasks no longer tear (text and line end are written in one step). Smaller: the button acts again after two lost edges following a press that ended the screensaver; a page decompressed for a client without gzip that fails or whose client leaves is closed instead of ending as a complete page, and `gzip;q=0` counts as *no gzip*; the MQTT stable-session timer starts after the connect (a slow TLS handshake no longer counts).
- **Setup wizard after a reset:** the dashboard offers the wizard again after every restart (*Reset settings*, *Erase everything*) — before, a browser that had seen it once in the same session (cookie `wnSetup=1`) went straight to the dashboard. The cookie now holds an ID of the start.
- **Own access point while the setup is not finished:** a phone on the node's access point got `401 Unauthorized` in the captive-portal sheet — the dashboard sent it to the setup wizard (admin login). Visitors on the own access point now always get the dashboard.
- **Latitude / longitude with a decimal comma:** the settings and the setup wizard accept `49,88` as well as `49.88` (stored with a point).
- **IT+ temperatures without float residue:** JSON, MQTT / Home Assistant and InfluxDB showed e.g. `-2.400002` °C for an IT+ sensor; the decoder now computes in tenths.
- **Home Assistant: wireless value groups only when delivered:** with wireless sensors on, temperature, humidity, pressure, wind, rain, UV and light (with sunshine) were always announced — a temperature-only station had ~30 entities that stayed *unknown*. Now a group is announced once a source has delivered it, at once also for a sensor added later; the node remembers it across restarts (no entity flapping, names and areas in HA stay), a source set to *Off* removes it.
- **Config portal: *Configure WiFi* shows only the network;** the node's fields moved to their own page *Setup* on the portal's start page. Both pages have *Save & restart* and *Back*; saving the Wi-Fi always restarts the node (before, a failed connect left the portal page standing without a word).
- **CPU frequency 240 MHz by default** (was 80): the web interface is noticeably faster; 80 MHz stays selectable for battery / solar nodes. Applies to new nodes and after *Reset settings*.
- **Placeholders by sensor ID:** `{rf300007DD_temp}` works like `{rf1_temp}` (custom screens, custom uploads, alarm texts) but keeps meaning that sensor when the list changes; the numbers still work. For a ★ sensor *Available placeholders* now inserts the key form (see *Logical sensors*), for other sensors this one. A line of a custom screen may have 63 characters (was 39).

**Fixes**

- **Value sources:** a quantity set to *Wireless N* now stays on the chosen sensor by its ID. Re-sorting the sensors in the status page or re-reading them after a restart no longer moves a value source to a different sensor (thanks Dirk). Settings saved before this update keep working and bind to the sensor the next time you save the value sources.
- **Value sources, binding corrected:** the settings page and the settings backup now use the sensor's ID instead of its number. Saving any setting while the chosen sensor was not received (e.g. right after a restart) could bind the source to a different sensor, and a source changed in the Wi-Fi portal was ignored. A sensor that gets a new ID with a battery change has to be chosen again.
- **Firmware upload:** a refused file shows the reason again (e.g. "different partition table"); the page cleared it before showing it.
- **Web interface:** the "not found" page breaks its lines instead of showing a literal `\n\n`.
- **Sensor naming fixes** (thanks Dirk, from an annotated screenshot): a temperature-only **WN30** that sends `0xFF` in the humidity byte is shown as WN30, not WH31; the dashboard labels a WH31 as *Thermo-hygro sensor* and a WN32P as *Indoor sensor* again (a field-name typo had labelled every thermo-hygro sensor *Temperature probe*); the LDS01 shows as *Distance sensor* instead of *Weather station*.
- **LDS01:** the API field `heaterActive` (and *heat* in the radio trace) is gone — the bit behind it marks the faster transmissions after a change of distance, not the heater. The heat-on count is its low byte only.
- **No phantom rain from one bad packet (Fine Offset, Bresser):** a rain total that drops or jumps up is now held until the next packet confirms it, like the Davis rain filter. A single corrupt packet whose checksum happened to pass is dropped instead of adding its whole total (and then the real total again) as rain; a real counter restart or a cloudburst is counted one packet later.
- **WS69 pressure:** the pressure extension after a WH65 frame is only taken with a station pressure of 300–1100 hPa. Random bytes that passed its checks by chance (about one WH65 frame in 65 536) could report e.g. 0 hPa as pressure and relabel the sensor as WS69.
- **Virtual WH31 at 100 % humidity:** a source reading 99.5 % or more (fog, a saturated BME280) sent a temperature-only WN30 frame, so the gateway lost the humidity just then. The humidity is now clamped to the WH31's 1–99 %.
- **Receive watchdog for the wireless-sensor receiver:** when the receiver has heard no frame of any kind and was not restarted for 10 min, it is restarted (logged; the count is in the radio trace header). One failed re-arm after a packet could otherwise leave a receiver that listens to one protocol only, without LoRaWAN or virtual sensors, deaf until a reboot.

**Updating**
- **From 1.1.1 (or a 1.x / 2.0.0 beta):** OTA with **`universal-weather-node-2.0.0.bin`** (the file *without* `-factory`; 1.x and 2.0.0-beta.2 or older must never get the factory file). ### Changes since 2.0.0-rc.8

- **Free stack on the status page:** the lowest free stack so far of the loop, web and upload tasks (FreeRTOS high-water mark), also in `/api/info` as `system.stackFree` (`loop`, `web`, `wxUpload`, bytes) — a value near 0 warns before a stack overflow like the one fixed in rc.8.
- **Reset buttons: cross-site check added** — `POST /api/settings/reset` (rc.6) was missing the same-origin check every other state-changing request has; a foreign web page could have reset the records or deleted the chart history in a browser logged in to the node.
- **Static IP: the message names the field** — a rejected static IP now says which field is missing or invalid (e.g. *static IP: gateway missing or invalid – nothing changed*) instead of only "invalid address"; on a newly set-up node the gateway is empty and has to be filled in together with the address (forum report).
- **PSRAM (Heltec V4) is used – it never was before:** up to rc.8 the build lacked the switch that lets the Arduino core start the PSRAM (`BOARD_HAS_PSRAM`), so a V4 ran with the V3's memory (the V4 radio trace in the forum: 87 KiB free). Now: the chart history, the 10-min wind window and – automatically – every buffer of 4 KB and more (radio trace, HTTPS / TLS, Wi-Fi) go to the PSRAM; on a V3 they stay in internal RAM as before. The memory figures (status page, `/api/info` `heapFree` / `heapMin` / `heapLargest`, the HTTPS memory guard) now count internal RAM only; a running PSRAM shows as its own status-page row and as `system.psram` in `/api/info`. A V4 whose PSRAM still does not start says so on the status page, and the boot log repeats the driver's reason (it goes to UART0 only, never seen over the V4's USB log).
- **Radio trace of a tester evaluated (forum, rc.8 with 21 Ecowitt sensors), and what came of it:**
  - **LDS01 recognised:** the laser distance sensor sends 19-byte Fine Offset frames (family `0x54`) every 80 s; it now appears in the sensor table with ID, signal and packets (mark it ★, name it). Its values are not decoded yet – the trace file shows the raw bytes.
  - **The trace file shows the reception rate:** per sensor, how many of the transmissions expected from its send interval arrived (`5 of 6 sent (83 %)`, the repeat that WH31, WH51, WN32, … send ~60 ms later is not counted twice), and how long packets waited for the firmware (*read delay*). Reason: the WS90 in the trace arrived only about one time in three although it was one of the strongest sensors – the next trace shows where that comes from.
  - Real frames of all 15 sensor models in the trace are now regression tests of the decoders; WH57 counts strikes as a running total (stays at its value between storms).
- **Display: the bottom line is fully visible again** — the six text lines of the classic screen (and of the config portal and the LoRaWAN result) were 11 px apart, so the last one (*RF: n sensor(s)* / uplink result) was cut off at the bottom on every V3 and V4 since the first version; now they fit the 64 px (forum report). The big-value screens moved their last line up by one pixel.
- **Display: three new options** under *Settings → Display* (all off by default, existing nodes look as before): **orientation** rotated by 180° (a V4 held like in Meshtastic showed the text upside down), **battery voltage top right** on every screen (the Heltec's LiPo, *USB* without one — also without the LiPo measurement for the outputs) and a **heartbeat LED** (the Heltec's white LED on GPIO35 flashes every 2 s while the firmware runs, also with the display off). Forum suggestions.
- **Settings page: typing in the Display and System tabs no longer lags** — every keystroke there cost the browser 0.2–0.4 s (Safari, Chrome on macOS and Windows; with a few characters the Mac's spinning wheel). Cause: the ~350 fields of the Alarms tab sat inside the settings form, reassociated with their own form by `form='aform'`; the browsers' autofill / password handling went through them on every keystroke in a field after them. The Alarms tab is now its own form after the settings form (measured: 0–1 ms per keystroke in every tab). Present since the Alarms tab exists.
- **Own measurement cycle, decoupled from LoRaWAN:** new setting *Measurement cycle* (*Settings → Measurement*, 10–600 s, default **30 s**). The values — status page, REST API, display, chart, records, alarms — are evaluated that often; LoRaWAN, MQTT and Loxone send on their own intervals as before, each with its own wind and rain window (a 300-s uplink still covers 300 s). Up to rc.8 the cycle was the LoRaWAN interval, even with LoRaWAN off — on a node with the default 300 s the dashboard values changed only every 5 minutes. The first cycle now completes 30 s after a start (was a whole interval), so values, display and the chart's first point are there at once. LoRa-only low-power mode keeps the LoRaWAN interval as its cycle. The setting formerly called *LoRaWAN / measurement interval* is now *LoRaWAN uplink interval*.
- **Log: cycle summary at most once a minute** (`[Cycle … wind samples] …`), and *Wind: no valid sample* only when it starts — with a short measurement cycle these lines pushed everything else out of the 4-KB log.
- **WN30 by its name:** a WH31 frame without humidity is the temperature-only WN30 (forum note) — model *WN30*, on the dashboard a temperature probe instead of a thermo-hygro sensor; IT+ and other temperature-only sensors likewise.
- **Radio-clock time of a WH31 with a time receiver** (e.g. the DNT version with DCF77, forum question): its time frame (family `0x52`, decoded as in rtl_433) is recognised and shown on the status page (*Radio-clock time*, with the sensor's ID and how long ago) and in the radio trace — it no longer appears as an unknown frame. Not used as the node's clock yet.
- **Custom series — own charts for soil moisture, lightning & co.:** *Settings → Sensors → Custom series*: a free-text name, a source (wireless sensor or the board's DS18B20 probes) and a value — soil moisture, leaf wetness, lightning (strikes per bucket from the sensor's counter), storm distance, PM2.5 / PM10, CO₂, soil conductivity, temperature, humidity, pressure, illuminance, UV, battery or super capacitor voltage. Each gets its own chart on the dashboard (24 h / 7 days), with the series' name as title. Up to 4 series on a V3, 8 with PSRAM (V4); memory (~0.9 KB each) only for series that are set up; saved with the history (format version 2, older saved histories are still read). `/api/history` carries them as `series`.
- **Available placeholders, with their current values:** a list under the custom screens, the custom uploads and the alarm texts shows every placeholder that has a value right now (wireless sensors with their name); a click inserts it at the cursor of the field used last. Loaded only when opened (`GET /api/placeholders`).
- **Display: two custom screens** under *Settings → Display*: title plus 5 small lines, or title plus a large value and 2 lines, filled with placeholders as for the custom uploads (`Garden {rf2_temp:.1}{u_temp}`) — in the device's units, with `{clock}`, `{date}`, `{ip}` and the unit labels on top; a missing value shows as `--`. A preview below each screen draws it with the current values, also before saving (redrawn while typing, at most one request at a time, or with a button) (`POST /api/display/preview`). Tick them under *Screens* to include them in the rotation.
- **Framework: Arduino-ESP32 2.0.17 (ESP-IDF 4.4.7)** instead of 2.0.11 (4.4.5) – the last 2.x release (PlatformIO `espressif32 @ 6.11.0`), no code changes needed. Measured on a V3: 1–4 KB more free internal RAM (after start 256 instead of 247 KB, lowest value 132 instead of 128 KB, largest block 127 instead of 123 KB). The new bootloader comes with the factory image; an OTA update keeps the old one, which works too (tested).
- **Dashboard names WN32P and WN32 by their role:** *Indoor sensor (temperature, humidity, pressure)* and *Outdoor sensor (temperature, humidity)* instead of the generic thermo-hygro sensor of the WH31 (forum suggestion).

**Check after the update** (release candidate: no conversion of old settings):
- a **value source set to *Off*** has to be set again (the value changed from `6` to `34`; otherwise it reads *Wireless 5*);
- value sources on ***Auto*** with ★ sensors now follow the order of your ★ list (arrows) — put the sensor that should feed the outputs first;
- wrong **rain-rate records** from a short MQTT / Loxone cycle can be cleared under Settings → System → Records.

- **Radio trace moved to the log page:** start, stop, download and discard are now on the password-protected log page (`/api/log`, box *Radio trace*); the status page keeps one compact row with the state and progress of a capture and a link there, so visitors no longer see buttons that end in a password prompt. After start / stop / discard the browser returns to the log page. The hex-ID field only appears when the filter *only this ID* is chosen. `/api/rf/trace` and `/api/davis/log` are unchanged.

After the start they are restored as soon as the clock is synced; the time the node was off shows as gaps. The 24-h values are only a hand-over (removed after the restore), so a power cut loses them and at most a day of hourly values. The settings always come first: the history is not saved if less than 16 KB of the 64-KB settings partition would stay free. New in `/api/info`: `system.settingsStoreUsed` / `settingsStoreFree`.
- **Rain rate over at least 5 minutes:** with a short cycle (MQTT or Loxone every few seconds) the rate was the rain of that cycle divided by its length, so one 0.2-mm tip in a 10-s cycle read 72 mm/h (two tips 144 mm/h) — in the status page, records, chart history, MQTT, weather networks, alarms and on the display. The rate now uses a rolling window of at least 5 minutes (a send window that is already 5 minutes or longer keeps its own); amounts are unchanged. Wrong rain-rate records from before can be cleared under Settings → System → Records (reset).
- **Readable links in dark mode:** links (also visited ones) use the teal accent colour instead of the browser's default blue / purple on all pages; the help page and the wind-direction calibration now follow the dark theme too (help: also the theme chosen on the dashboard), and form controls and scrollbars match the theme (`color-scheme`).
- **Bresser together with Ecowitt / Froggit or IT+ (timed switching):** instead of plain alternating (about half of the packets missed) the receiver learns each sensor's send interval from its packets and switches to that sensor's data rate about 1 s before its next packet is due; in between the data rates are listened to in turn as before (finds new sensors). With sensors marked ★ only those are followed. Simulated 98–100 % of the packets for a Bresser station with a WH65, WS80 or WH31; field test pending. Status page: *timed reception for n sensors*. New module `src/rf_schedule.cpp` (host-tested).
- **Wireless sensor table updates itself:** under Settings → Sensors newly received sensors are appended every 5 s and signal / values refreshed while the page is open (new `GET /api/settings/rfsensors`, the table alone); cells with a field — a name being typed, a changed state — are never replaced. It only refreshes while the *Sensors* tab is shown and no firmware upload runs (the web server keeps a single login nonce; a refresh during an upload made the upload start over and ask for the password).
- **Wireless sensor type *All types*:** keeps listening to Bresser, IT+ and Fine Offset with timed switching and stores nothing (unlike *Auto*, which stops at the first type it finds) — to see everything in range or for sensors of several brands. Parameter 50 value `15`.
- **Value sources: every wireless sensor 1–32** (was 1–4): the source lists offer every sensor that is received or ★ (with its name and ID, no empty placeholders); *Auto* still only looks at 1–4. **Changed parameter value:** *Off* is now `34` (was `6`; Wireless n = n + 1, i.e. `2`–`33`) — **a value source set to *Off* has to be set again once after the update** (it would otherwise read Wireless 5).
- **Value source *Auto* follows your ★ order:** with ★ sensors *Auto* takes, after the board sensor, the first ★ sensor (in the order of the ★ list, arrows on the settings page) that delivers the value — all ★ sensors, not only the first four, and the order you set is the priority (before: wireless 1–4 in Ecowitt's sensor order). Sensors that are not ★ are no longer used by *Auto* while any sensor is ★. Without ★ sensors nothing changes (wireless 1–4, Ecowitt's order). **Check the value sources after the update** if you rely on *Auto* with several sensors delivering the same value.
- **Pulse inputs settle after the start:** wind, rain and the AUX pulse input / 2nd anemometer are not counted for the first 10 s after the start (a burst on the wind line right after an update showed as a 226-km/h gust in the chart history; the records were not affected, the clock was not set yet).
- **Reset values with buttons:** under Settings → System → *Reset values* buttons (with a confirmation, effective at once, no *Save*): reset the records (today to this year, or all incl. all-time), the new **Delete chart history** (both ranges, also the copy in flash — e.g. to remove an outlier), **Reset rain statistics** (today … year, last rain, rain since start, also the flash copy), **Reset sunshine duration** and, on PCB v2.0, **Reset AUX pulse total** (before only by downlink / MQTT command). * The node now receives up to **32** wireless sensors at the same time (was 4) and *Wireless sensor IDs* takes up to 32 IDs — a fixed table reserved at start, no per-sensor memory allocation at run time (no heap fragmentation). Each sensor has a number 1–32 (`rfSensors[].slot`): its position in the ID list, else the reception order. Only 1–4 can be value sources — *Wireless 1–4*, *Auto* and parameters 45–49 keep their meaning; sensors 5–32 are reported everywhere but never feed the main values.

**Home Assistant: one device per wireless sensor** — see [Wireless sensors in Home Assistant](docs/mqtt-home-assistant.md#wireless-sensors-in-home-assistant).

Sensors not in the list (neighbours) get no device; with an empty list there are none (the status page and the settings hint say so).

**Radio trace ("Funk-Mitschnitt") for support** — see [Capturing a radio trace for us](docs/wireless-sensors.md#capturing-a-radio-trace-for-us).
* Status page, box *Wireless sensors*: **Start capture** for 5 / 15 / 60 min, recording all packets, only unknown / failed packets, or one sensor ID; progress (packets, buffer fill, time left), *Stop*, *Discard* and **Download diagnostic file** (`uwn-rftrace-<hostname>-<YYYYMMDD-HHMM>.txt`).

## 2.0.0-beta.2

Firmware binary: `universal-weather-node-2.0.0-beta.2.bin` (application image for OTA or USB). Same hardware support and beta status as 2.0.0-beta.1. **Update the payload decoder on ChirpStack/TTN first** (binary format version 4). New settings keep the previous behavior by default (MQTT interval 0 = like the LoRaWAN interval, wind values *interval*, value sources *Auto*, wireless sensors off); the wind sample interval default changes to 1 s for new installations, stored values are mapped to 1 s or 3 s.

**Wireless sensors and value sources**
* **Wireless sensors (Bresser, 868 MHz):** the LoRa chip receives Bresser 5/6/7-in-1 stations and other Bresser sensors between LoRaWAN uplinks (setting *Wireless sensors*, parameter 44, optional ID filter). Values on the status page and as `rfSensors` in `/api/data` / MQTT. Uses a fork of BresserWeatherSensorReceiver (MIT) in `lib/`, adapted to the shared transceiver and RadioLib 7.
* **Value sources:** per group (temperature/humidity, wind, rain, UV, light) *Auto* (board first, then wireless 1–4 with values not older than 5 min), *Board*, *Wireless 1–4* or *Off* — for LoRaWAN, MQTT/JSON, Home Assistant, weather networks, history and display (settings, portal field `srcs`, parameters 45–49). Wireless wind is aggregated per path like the anemometer (interval / 10 min); rain only adds increases of the selected source, so switching never jumps. New: `sources`, `lightLux`, `radioBatteryLow` in JSON; CayenneLPP Ch 15/16; wireless UV index; temperature/humidity no longer require a BME280 (pressure still does). Decoder updated (versions 1–4).

**LoRaWAN**
* **Compact binary format version 4** (always sent; decoder reads versions 1–4 — update it on ChirpStack/TTN **before** the firmware): variable-length presence mask (1–6 bytes instead of 4), UV voltage and index as separate fields (bits 31/32, no flag byte), new fields value sources (33) and illuminance (34), Victron values as separate fields (26, 35–41) instead of a fixed 14-byte block. A value that is not available takes no space; no existing value was removed. Typical station 1–3 bytes smaller than in 2.0.0-beta.1, minimal packet 3 instead of 6 bytes.
* Rejoin automatically after 288 uplinks in a row without any downlink (3 × the ADR acknowledgement window); if that does not help, the threshold doubles up to 2304 uplinks, any downlink resets it. A session that had stopped receiving downlinks — uplinks fine, ADR stuck at SF12, queued commands never delivered — previously stayed that way until the next restart.
* Failed joins are retried after 1, 2, 4 … minutes, at most every 60 min, instead of every minute — protects the join duty cycle and the DevNonce budget during network outages.
* **LoRaWAN airtime:** the uplink interval is stretched automatically to keep 1 % airtime at slow data rates (shown on the status page).

**Measurement and aggregation**
* **Separate aggregation per path:** LoRaWAN, MQTT and the weather networks keep their own windows; one send no longer resets the values of another. Rain: one running total, each path reports the difference since its own last send (interface unchanged).
* **MQTT interval** (setting, parameter 41): MQTT can publish faster than LoRaWAN, e.g. every 5 s; `0` keeps the old behavior (like the LoRaWAN interval).
* **Gust = highest 3-s mean** (WMO) instead of the highest single sample; **wind sample interval** 1 s (new default) or 3 s — other values map to a step (parameter 2 keeps working).
* **Wind values per path** (parameters 42/43): *interval* (since the last send, for downstream aggregation such as Grafana) or *10 min* (WMO values of the last 10 minutes from a 10-min ring buffer).
* **Weather networks** always get 10-min WMO wind values, independent of their upload interval.
* BME280 read every 10 s (at least once per base cycle) instead of every sub-sample. Docs: new section *Measurement and Aggregation*.

**Derived values, statistics and networks (all computed on the node)**
* **Derived values:** dew point, feels like (wind chill / heat index), cloud base, compass wind direction, 3-h pressure tendency with a weather trend, 1-h temperature trend, rain last hour / 24 h / yesterday and the time of the last rain, sunshine duration today / yesterday (Bresser 7-in-1 light), frost / fog / sultry warnings — in JSON/MQTT, Home Assistant (warnings as binary sensors), status page and dashboard tiles. The decoder adds dew point, feels like, cloud base, compass text and warnings from the decoded values (payload unchanged).
* **Weather networks:** Windy (PWS API v2) and openSenseMap (senseBox, sensor-ID mapping); dew point, rain of the last hour and UV index to the networks that take them; wind chill / heat index to Weathercloud.
* **Firmware update check** (optional, daily): newer version on the status page, in JSON and Home Assistant.
* History stores the rain per bucket in 0.01 mm (was 0.1 mm).

**TFA / LaCrosse IT+ wireless sensors**
* *Wireless sensor type* (web settings, portal `rfproto`, parameter 50): Bresser or TFA / LaCrosse IT+ temperature/humidity sensors (17.241 and/or 9.579 kbit/s, alternating every 5 s with both; Bresser + IT+ alternating is selectable but not recommended). IDs `170000xx` / `090000xx`, `protocol` in `rfSensors`. New library `lib/TfaWeatherSensorReceiver` (own, MIT, same pattern as the Bresser fork). Decoder checked against a published frame; not yet tested with real sensors. WeatherHub / Mobile Alerts not supported yet.

**Hardware (PCB v2.0)**
* **J18 DC jack** 5.5 × 2.1 mm (optional THT, LCSC C381116) parallel to J3 for 12 V / 24 V plug-in supplies, centre positive, up to 24 V / 5 A; F7, D1 and R45 moved beside it, VIN paths 1.5 mm wide. Case: knock-out in the left wall. Gerber/BOM/CPL/THT list regenerated, DRC clean.

**Web settings**
* **Wi-Fi network on the web settings page:** name and password can be changed in normal operation. The new network is tested for 60 s without a restart and only stored if the node connects; otherwise it returns to the previous network and shows a notice. *Store without test* pre-provisions a network that is not in range yet.

**Robustness (review of the whole firmware)**
* **Wireless sensors:** freshness is judged **per value** (a station that keeps sending wind but loses its temperature part drops only the temperature after 5 min; `stale` in `rfSensors`, *(stale)* on the status page) — also for the Bresser 6-in-1, whose library flags were cumulative (fork change 8). Sensor places are freed after 5 min of silence and when the ID list changes; IT+ battery changes are re-learned. Rain after a reception gap is spread instead of spiking the rain rate; values stay stale across the 49-day `millis()` wrap.
* **LoRaWAN:** the session is saved after every uplink; the EU868 1 % duty cycle is enforced by RadioLib (a too-early uplink is deferred, not counted as a failure; safe across the `millis()` wrap); send paths are at most 2 s early instead of half a cycle (LoRaWAN no longer sends more often than set); downlink commands only on FPort 1; the binary and CayenneLPP encoders leave out non-finite values; exact 32-bit AUX totals in CayenneLPP; the decoder reports truncated or unknown payloads in `errors`.
* **Inputs:** the user button works again after low-power sleep (the wake-up left its interrupt level-triggered) and press/release events can't be lost; no double count of a pulse just before light sleep; any number of PCNT counter wraps; rain reset (`0x01`) no longer shortens per-uplink rain amounts; BME280 readings outside its range (−40…85 °C, 300…1100 hPa, 0…100 %) are dropped; VE.Direct `---` means unavailable; wind fields are left out when a window has no valid sample; wind 2 gust is a 3-s gust, its mean pulse-weighted.
* **Settings:** stored values are re-checked at boot (out-of-range values reset or clamped); heater full-power temperature ≤ switch-on temperature; time-zone changes are applied on the main task.
* **Web / Wi-Fi / MQTT:** Wi-Fi change keeps the previous network from the driver (a short disconnect could store the untested one), needs DHCP for another network and a gateway/DNS answer before it is kept; portal values with `'` are no longer cut off, secrets are not prefilled, the admin password protects `/update` and ArduinoOTA; settings posts from other sites are refused and missing fields keep their value; MQTT/HA IDs sanitised, full MAC for unnamed nodes; MQTT reconnect back-off up to 5 min with shorter timeouts; update-check tag validated and escaped, GitHub lists streamed; weather-network uploads after an outage restart their averaging window; rain before the first time sync counts as today; dashboard wind unit follows the device setting.
* **Derived values:** rain 1 h / 24 h never longer than the window; 1-h / 3-h trends only after enough history; version compare ignores `-dirty` and case.

**Status page and diagnostics**
* Status page: new **LoRaWAN** box (data rate/SF, channel, TX power, device address, frame counter, last downlink with RSSI/SNR, uplinks since the last downlink vs. the rejoin limit, rejoins since start) and in **Device** the CPU temperature, the cause of the last restart and the minimum free heap.
* `/api/data` and MQTT JSON: `cpuTemp`/`cpuTempUnit` are now always included (previously debug mode only), plus `resetReason`; Home Assistant discovery offers both (*CPU Temperature*, *Last Restart*) without debug mode.
* Status page: the wireless receiver's pause during a LoRaWAN uplink is shown as normal (*paused for a LoRaWAN uplink*) instead of as an error.

## 1.1.1

**Fixes:**
* BME280 is now hot-pluggable: it was only detected once at boot, so a sensor connected later was ignored until reset, and an unplugged one kept reporting its last values as present. While absent it is now re-probed every sub-sample and fully re-initialized when it answers again (also restoring the humidity config a power-cycled chip loses); a failed or NAN measurement marks it absent.
* BME280 cycle averages are divided by the number of valid BME280 readings instead of all sub-samples, so a sensor (un)plugged mid-cycle no longer skews the average.

## 1.1.0

**Payload changes — update `decoder.js` in ChirpStack together with this firmware** (the new decoder still decodes payloads from older firmware):
* Compact binary format **version 2**: in imperial mode rain is encoded ×1000 (0.001 in) and pressure ×100 (0.01 inHg) — previously a single 0.2 mm tip (0.008 in) was sent as 0 and pressure had ≈ 3.4 hPa resolution; rain since start is `u32` (previously wrapped above 6553.5 mm). Metric values are unchanged.
* CayenneLPP: imperial pressure is sent with 0.01 inHg resolution (decoder divides by 10 when the imperial bit is set); debug channels Ch203 (free heap) and Ch204 (uptime, 0.1 h) are now *Generic Sensor* (previously saturated at 327).
* All values are rounded instead of truncated and clamped instead of wrapped; the decoder no longer rounds rain to 0.1.

**Fixes:**
* Wind-direction calibration was lost when the portal closed after *Save Calibration* — the portal wrote its pre-calibration state back.
* DS18B20 probes were never detected on PCB Rev 1.3: the bus was searched once at boot while its supply was still switched off. It is now searched every cycle after power-up, which also makes the probes hot-pluggable as documented.
* Live web/REST rain values (`rain`, `rainRate`) were overwritten by every 3 s sub-sample (mostly 0, or 240 mm/h for a single tip); they now show the last completed cycle.
* `rainMMSinceStart` did not survive restarts as documented (`RTC_DATA_ATTR` is re-initialized on every non-deep-sleep boot); it now survives restarts and watchdog resets and only resets on power loss or downlink `0x01`.
* Dashboard history ages broke after 49.7 days of uptime (`millis()` wrap); it now uses a 64-bit uptime. Same for the debug uptime and the display timeout.
* A short button press showed stale display content; the display is now redrawn, and the boot screen shows a first real reading.
* PCNT counter wrap (every 32767 pulses) produced a negative delta: one rejected wind sample per wrap, and negative rain after ≈ 6553 mm.
* Heap leak on every failed join attempt (a new `LoRaWANNode` was allocated per retry).
* Possible race in `webApiStop()` that could restart the web server right before the config portal took port 80.
* Input validation: wind-direction offset limited to ±180° in the portal (out-of-range NVS values no longer produce 65xxx°); web settings and MQTT values outside the int16 range are rejected instead of wrapping (`65836` → `300`), and invalid web settings are reported instead of silently ignored.
* Default MQTT port is 1883, matching the default "no TLS" mode (was 8883).

**Other:** `ParamId` enum instead of magic numbers (`applyDownlinkParam()` renamed to `applyParam()`); dashboard/log HTML moved from `web_api.cpp` into `include/`; `partition_repair` renamed to `partition_check` (it only detects); compact binary encoder split out as host-testable C++ with new decoder and round-trip tests; generated headers are no longer tracked and only release builds are copied to `firmware/`; README: build & flash, tests, LoRaWAN session & join, corrected payload sizes and data-rate limits, RC filter values (incl. wind-direction filter C11 = 1 µF), rain accumulator and DS18B20 behavior.
