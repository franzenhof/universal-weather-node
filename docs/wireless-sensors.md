# Wireless Sensors (Bresser, TFA IT+, Ecowitt, 868 MHz)

Supported sensors, sensor IDs, the automatic search and how to choose per value whether a board or a wireless sensor feeds the outputs. With the default *Wireless sensor type* **Auto (search)** the node finds the first station it hears by itself — details in the [Settings Reference](settings.md#settings-reference).

[← back to README](../README.md)

The node can additionally receive wireless sensors on 868.3 MHz (FSK) **with the existing LoRa chip, no extra hardware**: **Bresser** sensors — e.g. the **7-in-1** station (wind, rain, temperature, humidity, UV, light), 5-in-1 and 6-in-1 stations, thermo/hygro, soil, lightning and leakage sensors — , **TFA Dostmann / LaCrosse IT+** temperature/humidity sensors or **Fine Offset** sensors sold as **Ecowitt** and **Froggit** (details below; IT+ and Fine Offset not yet tested with real sensors). Switch it on with *Wireless sensors* and choose the family with *Wireless sensor type* (web settings *Measurement*, portal, or parameters 44 and 50).

- **Shared radio:** the SX1262 listens for the sensors whenever LoRaWAN does not need it. Before every uplink (and its two receive windows) and every join, the firmware stops the reception and restarts it afterwards. LoRaWAN is not affected; a sensor packet that arrives during an uplink is lost — Bresser sensors repeat every 12–16 s, IT+ sensors about every 4 s, so at a 60 s LoRaWAN interval roughly 5 % of the packets are missed, and only the latest values are kept anyway.
- **Sensor IDs:** with *Wireless sensor IDs* empty the node accepts any sensor of the selected type in range (up to 4); IT+ sensors and most Ecowitt / Froggit sensors get a new ID with every battery change. The status page lists every received ID with RSSI — enter yours (hex, comma-separated) to ignore the neighbours'. A sensor not heard for 5 minutes gives up its place to a new one (e.g. after a battery change), and changing the ID list clears the sensor table. An IT+ sensor that reports a fresh battery takes over the place of a silent IT+ sensor on the same data rate after 1 minute (with an ID list, only if the new ID is in it).
- **Output:** status page box *Wireless sensors (868 MHz)* and the JSON field `rfSensors` in `/api/data` and the MQTT data topic — one object per sensor with `id`, `type`, `protocol` (`Bresser`, `IT+ 17.241 kbit/s`, `IT+ 9.579 kbit/s`, `Fine Offset`), for Fine Offset also `model` and `channel`, `rssi`, `ageSec`, `batteryOk` and, as far as the sensor sends them, `temp`, `humidityPct`, `windSpeed` / `windGust` / `windDirDeg` (the sensor's own mean and gust), `rainTotal` (the sensor's running total, resets on a battery change), `uvIndex`, `lightLux`, `soilMoisturePct`, `lightningCount` / `lightningDistKm` (WH51 / WH57, JSON and status page only), `supercapV` (voltage of the solar-charged super capacitor — only WS85 / WS90 send it; the key is missing for all other sensors), and `stale` — the values not received for more than 5 minutes although the sensor still sends others (e.g. a failed temperature element); the status page marks them *(stale)*. Units follow the unit settings. Which of these values go into LoRaWAN, MQTT, Home Assistant, the weather networks and the history is set with the [value sources](#value-sources).
- **Low-power mode** is not available while wireless sensors are on (the chip stays in receive mode, ~5 mA).
- **TFA Dostmann / LaCrosse IT+ sensors** instead of Bresser: set *Wireless sensor type* (web settings, portal field `rfproto`, parameter 50) to *TFA / LaCrosse IT+*. Supported: temperature / humidity sensors at **17.241 kbit/s** (TFA 30.3143.IT, 30.3144.IT, 30.3147.IT, 30.3157.IT, 30.3159.IT; TX21/25/27/29-IT) and **9.579 kbit/s** (TFA 30.3155.WD, 30.3156.WD; TX35-IT). With *both data rates* the receiver alternates every 5 s (the sensors send about every 4 s); choose the single rate if you know it. **Bresser and IT+ at the same time** is only possible alternating (*Bresser + TFA IT+ alternating*: 17 s Bresser, 5 s each IT+ rate) — the single SX1262 can listen to one data rate / sync word at a time, so packets of both families are missed (e.g. a good part of the Bresser wind packets, which makes wireless wind coarser). **Not recommended**; use one sensor family where possible. IT+ sensors only have a 6-bit ID that changes with every battery change — they appear as **`170000xx`** (17.241 kbit/s) or **`090000xx`** (9.579 kbit/s); after a battery change, update *Wireless sensor IDs* (or leave the list empty). **Not yet tested with real sensors** — the decoder is checked against a published frame. TFA *WeatherHub* / Mobile Alerts sensors are not supported yet (scrambled 6 kbit/s format; see `lib/TfaWeatherSensorReceiver/README.md`).
- **Fine Offset / Ecowitt / Froggit sensors** (868 MHz versions only): set *Wireless sensor type* to *Fine Offset / Ecowitt / Froggit* — or, together with IT+ thermo-hygro sensors, *TFA IT+ 17.241 kbit/s + Fine Offset*: both use 17.24 kbit/s with the same sync word and are received **in the same phase, nothing is missed**. Supported (formats from the rtl_433 documentation, each frame checked by CRC-8 and checksum): outdoor arrays **WH65 / WS69** (e.g. Froggit WH3000SE / WH4000SE; WS69 with pressure), **WS68**, **WS80**, **WS85**, **WS90**; thermo-hygro **WH31 / WN31 / DP50** (8 channels); probes **WN34 / DP35 / DP150**, **WN38** (globe temperature — select them as a temperature source deliberately); rain **WH40 / DP80**, **WN20** (the WS80, WS85, WS90, WS68 and WH65/WS69 arrays are solar-powered with a super capacitor, AA batteries only as backup — WS85 / WS90 also report the capacitor voltage); soil moisture **WH51 / DP100** and lightning **WH57 / DP60** (JSON and status page only). IDs read **`FFiiiiii`** — `FF` the model code, `iiiiii` the sensor ID as the Ecowitt app or rtl_433 shows it, e.g. WS90 `9000342B`, WH31 channel 1 `300001C3`. The old **WH24** sends the same frame as the WH65 with other units and can't be told apart — values follow the WH65. Not supported: WH25/WH32, air-quality, leak and WH1080 sensors, 433/915 MHz versions. **Not yet tested with real sensors.**
- Decoding: Bresser with a fork of [BresserWeatherSensorReceiver](https://github.com/matthias-bs/BresserWeatherSensorReceiver) (MIT) in `lib/BresserWeatherSensorReceiver` — adapted to share the transceiver with LoRaWAN and to RadioLib 7; changes in its `FORK.md`. IT+ with `lib/TfaWeatherSensorReceiver` (own, MIT, same usage pattern — kept self-contained so it can become a stand-alone library). Fine Offset with `lib/FineOffsetSensorReceiver` (own, MIT, written from the rtl_433 format documentation, no code copied). 433 MHz (OOK) sensors are not supported (the SX1262 has no OOK receiver).

## Idea: Davis wireless (Vantage Pro2 / Vantage Vue ISS)

**Not implemented — looking for a tester.** The EU versions of the Davis Vantage Pro2 / Vue ISS and the anemometer transmitter 6332 also transmit on 868 MHz, and the protocol is publicly documented by the community (e.g. the VPTools project). Receiving it with the Heltec's SX1262 is possible in principle, but harder than Bresser or Ecowitt:

- **Frequency hopping:** every packet on the next of 5 channels in a fixed sequence, at a fixed interval (about 2.56 s, depending on the transmitter ID). The receiver must stay synchronised with the hop sequence and timing; after a gap it has to re-acquire the transmitter, which takes several seconds.
- **Rotating data:** wind comes in every packet, temperature, humidity, rain (bucket-tip counter with wrap-around), UV, solar radiation and battery in rotating message types.
- **Exclusive use of the radio:** the radio has to follow the hop sequence continuously, so it would be a **Davis-only mode**:
  - **no LoRaWAN in parallel** — every uplink with its receive windows breaks the synchronisation (at most occasional uplinks with gaps in the Davis data);
  - **no other wireless sensors in parallel** (Bresser, Ecowitt, TFA);
  - outputs via Wi-Fi only (dashboard, MQTT / Home Assistant, weather networks, Loxone).
- It can only be developed and verified with a real **868 MHz Davis ISS** — the timing can't be tested against recorded frames alone.

**You have a Davis Vantage Pro2 / Vue (868 MHz) and would like to test?** Please get in touch (GitHub issue or the [forum thread](https://wetterstationsforum.info/viewtopic.php?t=3273)). Wired Davis sensors (6410 anemometer, AeroCone rain gauge) are already supported via the [custom PCB](pcb.md).

## Value Sources

Board sensors and wireless sensors can measure the same quantities. For each group one setting (web settings *Measurement*, portal field `srcs`, parameters 45–49) decides which sensor feeds **all** outputs — LoRaWAN, `/api/data` / MQTT, Home Assistant, weather networks, history, display:

| Group | Board sensor | Wireless sensors |
|-------|--------------|------------------|
| Temperature / humidity | BME280 | Bresser 5/6/7-in-1, thermo/hygro; TFA / LaCrosse IT+ (humidity only if the sensor has it); Ecowitt / Froggit WH65/WS69, WS68/80/85/90, WH31 (WN34/WN38: temperature only) |
| Wind (mean, gust, direction always together) | Davis anemometer + vane | Bresser 5/6/7-in-1; Ecowitt / Froggit WH65/WS69, WS68/80/85/90 |
| Rain | tipping-bucket gauge | Bresser 5/6/7-in-1; Ecowitt / Froggit WH65/WS69, WS85/90, WH40, WN20 |
| UV | analog UV input (PCB v2.0) | Bresser 6/7-in-1 (UV index); Ecowitt / Froggit WH65/WS69, WS80/90 |
| Light | – | Bresser 7-in-1 (lux); Ecowitt / Froggit WH65/WS69, WS80/90 |

Pressure always comes from the BME280; the DS18B20 probes, wind 2 and AUX are unaffected.

- **Auto** (default) works like a PC boot order: the board sensor first (if enabled / detected), then wireless 1–4 — the first one that currently delivers the value is used. A wireless sensor counts as long as its last packet **with that value** is at most **5 minutes** old — judged per value, so a dead or out-of-range sensor drops out automatically, and so does a single failed measurement of a sensor that keeps sending the others. With only the board sensors (no wireless sensors) *Auto* behaves exactly as before.
- **Board sensor** / **Wireless n** use exactly that sensor and nothing else; if it does not deliver, the value is left out (no fallback). *Off* never reports the group.
- **Wireless 1–4** are the IDs in *Wireless sensor IDs* in their order; with an empty list, the sensors in the order they were first received since start (so better enter the IDs — the settings page lists the received ones).
- **Wind** from a wireless sensor uses the sensor's own mean, gust and direction per packet (every 12–16 s), aggregated per send path exactly like the board anemometer: *Interval* (time-weighted mean, highest gust, vector-mean direction since the last send) or *10 min*. The weather networks get the 10-min values. The gust is the sensor's gust, not the board's 3-s gust.
- **Rain**: the running total (*rain since start*) only adds the increases of the selected source — the board's tipping-bucket pulses or the difference between two packets of the wireless sensor's total. Switching the source never produces a jump; a battery change of the wireless sensor (its total restarts) counts from zero again. Missed packets (during an uplink, interference, weak signal) lose no rain: the sensor sends its total, so the next packet received carries the increase — after a gap of more than 5 minutes the missed rain is added gradually (at its average rate over the gap, within at most 1 h), so the total stays right without a rain-rate spike.
- **Where the value came from** is visible on the status page (*Sources*, while wireless sensors are on or a source is set other than *Auto*), in JSON as `sources` (`{"tempHum": "board", "wind": "radio:39582376", …, "light": "none"}`, plus `radioBatteryLow` when a wireless sensor in use reports a low battery) and in the LoRaWAN payload (CayenneLPP Ch 16 / binary field 33) — these three only while wireless sensors are on.
- Not (yet) sent to the weather networks: UV and light.
