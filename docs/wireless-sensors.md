# Wireless Sensors (Bresser, TFA IT+, Ecowitt, Davis, 868 MHz)

Supported sensors, sensor IDs, the automatic search and how to choose per value whether a board or a wireless sensor feeds the outputs. With the default *Wireless sensor type* **Auto (search)** the node finds the station by itself — details in the [Settings Reference](settings.md#settings-reference) and [Auto search](#auto-search).

### Auto search

*Auto (search)* listens to Bresser, IT+ 17.241 kbit/s + Fine Offset and IT+ 9.579 kbit/s in turn and saves the type once **one sensor sent at least 3 valid packets within 10 minutes with a mean signal of −105 dBm or better** (on the Heltec V4, whose front end reads about 20 dB higher, −85 dBm). A weak sensor at the edge of the range — typically a neighbour's — no longer ends the search; it stays in the table as *received*. If after **30 minutes** only weak sensors were heard, the best of them (most packets, then strongest) is taken anyway and marked **signal very weak** on the status page and in the setup wizard. While searching, the status page lists every candidate with its packets and signal. The wizard's station step shows the type found with a **Search again** button (back to *Auto*); a fixed sensor type is never changed.

[← back to README](../README.md)

The node can additionally receive wireless sensors on 868.3 MHz (FSK) **with the existing LoRa chip, no extra hardware**: **Bresser** sensors — e.g. the **7-in-1** station (wind, rain, temperature, humidity, UV, light), 5-in-1 and 6-in-1 stations, thermo/hygro, soil, lightning and leakage sensors — , **TFA Dostmann / LaCrosse IT+** temperature/humidity sensors or **Fine Offset** sensors sold as **Ecowitt** and **Froggit** (details below; Fine Offset **tested with real frames** (forum radio traces on a Heltec V4, November 2026): WS90, WH31 / WN31 (also with radio clock), WN30, WN34, WN38, WH40, WN20, WH51, WH52, WH55, WH57, WN35, WH45, WN32P, WN32; **TFA IT+ 17.241 kbit/s reception confirmed with a real temperature-only sensor** (a neighbour's, CRC-checked, plausible values); WS80, WS85, WS68, WH65 / WS69, WH41, WH43, WH46 and IT+ 9.579 kbit/s decoded from published frames, not yet tested with real sensors). Switch it on with *Wireless sensors* and choose the family with *Wireless sensor type* (web settings *Measurement*, portal, or parameters 44 and 50).

- **Shared radio:** the SX1262 listens for the sensors whenever LoRaWAN does not need it. Before every uplink (and its two receive windows) and every join, the firmware stops the reception and restarts it afterwards. LoRaWAN is not affected; a sensor packet that arrives during an uplink is lost — Bresser sensors repeat every 12–16 s, IT+ sensors about every 4 s, so at a 60 s LoRaWAN interval roughly 5 % of the packets are missed, and only the latest values are kept anyway.
- **Sensor IDs and numbers:** the node keeps up to **32** sensors at a time (a fixed table reserved at start — no memory is allocated per sensor at run time, so the heap does not fragment over months of operation). Each sensor is ★ *Mine*, ○ *Received* or ✕ *Hidden* — see [Mine, Received, Hidden](#mine-received-hidden). Each stored sensor gets a **number 1–32** (*Wireless n*, JSON `slot`): the ★ sensors first in their order, then the others in the order they were first received. All of them appear on the status page, the dashboard, in `/api/data` `rfSensors`, on MQTT (`<prefix>/rf/<ID>`) and in Loxone (`rf<n>_…`); only **1–4** can be chosen as [value sources](#value-sources). [Home Assistant](mqtt-home-assistant.md#wireless-sensors-in-home-assistant) gets one device per **★ sensor only** (so the neighbours' sensors stay out). IT+ sensors and most Ecowitt / Froggit sensors get a new ID with every battery change — mark the new ID ★ again. A sensor not heard for 5 minutes gives up its place to a new one (e.g. after a battery change); a ★ sensor always finds a place (it takes the one of the other sensor heard longest ago). An IT+ sensor that reports a fresh battery takes over the place of a silent IT+ sensor on the same data rate after 1 minute (with *Only my sensors*, only if the new ID is ★).
- **Output:** status page box *Wireless sensors (868 MHz)* and the JSON field `rfSensors` in `/api/data` and the MQTT data topic — one object per sensor with `id`, `type`, `protocol` (`Bresser`, `IT+ 17.241 kbit/s`, `IT+ 9.579 kbit/s`, `Fine Offset`), for Fine Offset also `model` and `channel`, `rssi`, `ageSec`, `batteryOk` and, as far as the sensor sends them, `temp`, `humidityPct`, `windSpeed` / `windGust` / `windDirDeg` (the sensor's own mean and gust), `rainTotal` (the sensor's running total, resets on a battery change), `uvIndex`, `lightLux`, `soilMoisturePct`, `lightningCount` / `lightningDistKm` (WH51 / WH57), per-sensor values of the Fine Offset air quality, leak, leaf wetness, soil EC and indoor sensors (`pm25`, `pm10`, `pm1`, `pm4`, `co2Ppm`, `leak`, `leafWetnessPct`, `conductivityUsCm`, `pressure` — see below), `supercapV` (voltage of the solar-charged super capacitor — only WS85 / WS90 send it; the key is missing for all other sensors), and `stale` — the values not received for more than 5 minutes although the sensor still sends others (e.g. a failed temperature element); the status page marks them *(stale)*. Units follow the unit settings. Which of these values go into LoRaWAN, MQTT, Home Assistant, the weather networks and the history is set with the [value sources](#value-sources).
- **Low-power mode** is not available while wireless sensors are on (the chip stays in receive mode, ~5 mA).
- **TFA Dostmann / LaCrosse IT+ sensors** instead of Bresser: set *Wireless sensor type* (web settings, portal field `rfproto`, parameter 50) to *TFA / LaCrosse IT+*. Supported: temperature / humidity sensors at **17.241 kbit/s** (TFA 30.3143.IT, 30.3144.IT, 30.3147.IT, 30.3157.IT, 30.3159.IT; TX21/25/27/29-IT) and **9.579 kbit/s** (TFA 30.3155.WD, 30.3156.WD; TX35-IT). With *both data rates* the receiver alternates every 5 s (the sensors send about every 4 s); choose the single rate if you know it. **Bresser and IT+ at the same time** works with timed switching, see [several sensor families](#several-sensor-families-at-once). IT+ sensors only have a 6-bit ID that changes with every battery change — they appear as **`170000xx`** (17.241 kbit/s) or **`090000xx`** (9.579 kbit/s); after a battery change, update *Wireless sensor IDs* (or leave the list empty). The **17.241 kbit/s** rate is **confirmed with a real sensor** (a CRC-checked neighbour's temperature sensor, plausible values); the **9.579 kbit/s** decoder is checked against a published frame. TFA *WeatherHub* / Mobile Alerts sensors are not supported yet (scrambled 6 kbit/s format; see `lib/TfaWeatherSensorReceiver/README.md`).
- **Fine Offset / Ecowitt / Froggit sensors** (868 MHz versions only): set *Wireless sensor type* to *Fine Offset / Ecowitt / Froggit* — or, together with IT+ thermo-hygro sensors, *TFA IT+ 17.241 kbit/s + Fine Offset*: both use 17.24 kbit/s with the same sync word and are received **in the same phase, nothing is missed**. Supported (formats from the rtl_433 documentation, each frame checked by CRC-8 and checksum): outdoor arrays **WH65 / WS69** (e.g. Froggit WH3000SE / WH4000SE; WS69 with pressure), **WS68**, **WS80**, **WS85**, **WS90**; thermo-hygro **WH31 / WN31 / DP50** (8 channels; a WH31 frame without humidity is shown as the temperature-only **WN30**; a WH31 with a radio-clock receiver, e.g. the DNT version with DCF77, also sends its received time — shown on the status page as *Radio-clock time*, not used as the node's clock); probes **WN34 / DP35 / DP150**, **WN38** (globe temperature — select them as a temperature source deliberately); rain **WH40 / DP80**, **WN20** (the WS80, WS85, WS90, WS68 and WH65/WS69 arrays are solar-powered with a super capacitor, AA batteries only as backup — WS85 / WS90 also report the capacitor voltage); soil moisture **WH51 / DP100** and lightning **WH57 / DP60**. IDs read **`FFiiiiii`** — `FF` the model code, `iiiiii` the sensor ID as the Ecowitt app or rtl_433 shows it, e.g. WS90 `9000342B`, WH31 channel 1 `300001C3`. The old **WH24** sends the same frame as the WH65 with other units and can't be told apart — values follow the WH65. How a frame is checked and decoded, byte by byte: [Fine Offset frames, decoded by hand](fineoffset-frames.md). **LDS01** (laser distance, ID `54iiiiii`, every 80 s) is recognised and listed with signal and packets, its values are not decoded yet. Not supported: WH1080 / WH1050, Ecowitt IoT devices (WFC01 valve, AC1100 plug — their own two-way format with the gateway, not decoded), WittCam, 433/915 MHz versions. **Tested with real frames:** WS90, WH31 / WN31, WN30, WN34, WN38, WH40, WN20, WH51, WH57 (each a fixed test case in `test/firmware_fineoffset.cpp`); **not yet:** WS80, WS85, WS68, WH65 / WS69.

### Several sensor families at once

The SX1262 listens to one data rate at a time: Bresser, 17.241 kbit/s (IT+ and Fine Offset / Ecowitt / Froggit together) or IT+ 9.579 kbit/s. With a type that combines Bresser with the others (*Bresser + Fine Offset*, *Bresser + TFA IT+*, *All types*, or *Auto* while it searches) the receiver switches between them:

- **Timed switching:** every sensor sends at a steady interval (Bresser ~12 s, WS80 4.75 s, WH65 16 s, WH31 61 s …). After two packets of a sensor its interval is known; from then on the receiver switches to that sensor's data rate about 1 s before its next packet is due and stays until about 1 s after. If two packets are due at nearly the same time, the earlier one is taken first, then the receiver moves on to the other.
- **In between** the data rates are listened to in turn (17 s Bresser / 17 s Fine Offset / 5 s IT+), which finds new sensors and recaptures one that was missed several times.
- With sensors marked **★ mine** only those are followed; a neighbour's sensor does not take the receiver away from one's own.
- The status page shows *timed reception for n sensors* next to the receiver.

In a simulation this receives about 98–100 % of the packets of a Bresser station together with a WH65, WS80 or WH31 (plain alternating: about half). Two sensors that send at exactly the same moment still collide — on air as well. **Field test pending** — feedback with both brands is welcome.


  **Also decoded** — from published frames; ✓ = tested with a real frame (forum trace, November 2026) (same 17.24 kbit/s phase, received together with the others; the values below are per sensor — JSON / MQTT `rfSensors[]`, Home Assistant, Loxone, status page, dashboard — and never feed the node's main values, except temperature / humidity, which count like a WH31's):

## Mine, Received, Hidden

Every sensor the node hears is in one of three states — set them in **Settings → Sensors**, table *Wireless sensors* (a select per row, arrows for the order, then *Save*), or on the **status page** with the ★ / ✕ buttons next to each sensor:

| State | Stored and output | Number (`slot`) | Home Assistant device | Used by value source *Auto* |
|-------|------------------|-----------------|-----------------------|-----------------------------|
| ★ **Mine** | yes (JSON `rfSensors[].mine` = true) | first, in the order of the ★ list — also while not received, so the numbers never shift | yes | all ★, in their order (= priority) |
| ○ **Received** | yes | after the ★ sensors, in reception order | no | only while no sensor is ★ (wireless 1–4) |
| ✕ **Hidden** | **no** — not in the table, no number, not in REST, MQTT, Home Assistant, Loxone, value sources | – | no | – |

- **Only my sensors** (switch in the same tab, parameter 55): on = only ★ sensors are received at all, everything else is dropped like before when an ID list was set. Off = every sensor except the hidden ones. It has no effect while no sensor is ★. **Nodes updated from an older firmware:** with an ID list the switch starts **on** (exactly the old behaviour), without one **off**.
- **Hidden sensors in range:** a hidden sensor that is still heard is listed under *Hidden sensors in range* (settings, collapsed; heard within 10 min, at most 16) — set it to ○ or ★ there to unhide it. The status page shows "*n* hidden sensors in range".
- Hiding a sensor frees only its own place; changing ★ / the order only renumbers the others (their values stay).
- The lists can also be edited as text (*Show advanced options*: *Mine* = the ★ IDs in order, *Hidden*), in the config portal (fields `rfids`, `rfignore`, `rfonly`) and from scripts with `POST /api/rf/sensor` (`id`, `action=mine|received|hide|up|down`, Digest).

### Names, Ecowitt IDs, rain and lightning per sensor

- **Names:** give a sensor a name (e.g. *Hochbeet*, up to 24 characters) in the sensor table (*Settings → Sensors*) or in the setup wizard's station step. It is stored by sensor ID (also as text under *Show advanced options*: *Names*, `ID:name|ID:name`; in the settings backup) and shown on the dashboard card, the status page, as `name` in `rfSensors` / `<prefix>/rf/<ID>` and as the Home Assistant device name *&lt;name&gt; (&lt;model&gt;)*. Loxone keeps the numbers (`rfN_…`).
- **Ecowitt IDs:** the Ecowitt app and console show a shorter ID than ours — e.g. **181A2** for our **900181A2** (WS90: the family code in the top byte, then the sensor's ID); WH31 / WH32 / WN32P use only their 8-bit ID (our `300002B2` = channel 2, Ecowitt **B2**). Cards, status page and sensor table show both (*ID 900181A2 (Ecowitt 181A2)*, JSON `ecowittId`). You may type the **short form into the Mine / Hidden lists**: as soon as that sensor is heard, the entry is replaced by the full ID (in RAM; stored with the next *Save*). A short entry matches only Fine Offset sensors.
- **Rain per sensor:** `rainTotal` ("counter") is the sensor's **own counter since its last battery change or reset** — not a total of the node (a WH40 may show 731.7 mm, a WH65 6898.6 mm). The node computes **rain today** (since local midnight) and **rain in the last hour** from the counter's increments, with the same reset handling as the main rain path (a smaller counter = reset). Kept in RAM only (for up to 12 sensors): after a restart it counts again from then on.
- **Rain correction per sensor:** a fixed rain factor per sensor (*Settings → Sensors → Sensor calibration*, `ID:t:h:rain:…`), applied to the counter's increments. **WN20 — the normal way: rain factor 0.908**, e.g. `20001234:0:0:0.908` (no funnel area or tip size needed). The counting itself is right: one tip is 0.317 mm (corrected by Ecowitt in November 2026, formerly given as 0.28 mm), the sensor adds 0.3 mm per tip and 0.4 mm on every sixth into the 0.1 mm total it sends — 1.9 mm per 6 tips against 1.902 mm. Compared with a WH40 the WN20 still reads high, because its sensitive seesaw tips too early; the Ecowitt wiki (meshka.eu, section WN20, read 2026-11-23) gives a factor of about 0.91 for rain up to 5 mm/h — most of the rain in a year (0.908 is the same within 0.2 %). **Experimental: rate-dependent WN20 preset** (`…:wn20`, off by default) — the wiki gives **0.773 at 5–10 mm/h** (the seesaw tips early more often as the rate rises); higher rates are not measured yet (a further decrease is expected), so the node keeps **0.773 above 10 mm/h (unverified)**. The rate is that sensor's own rain of the last 10–20 minutes; the preset replaces a fixed rain factor for that sensor. Use it only if you want to compare it with a reference gauge; until the wiki has figures for heavy rain the plain factor is the safer choice.
- **WH40 preset** (`…:wh40`, off by default): the WH40's tip is really 0.1016 mm (0.004 in) but reported as 0.1 mm — the gauge under-reads by about 1.6 % (Ecowitt wiki by Gyvate, section WH40, which suggests a console gain of 1.022). The preset multiplies the increments by **1.016** and replaces a fixed rain factor — the same as the plain rain factor `…:0:0:1.016`; use whichever you prefer. The **WS69 / WH65** already reports the exact 0.254 mm step and needs no correction here (the console needs × 1.02).
- **Soil moisture (WH51):** besides the moisture % the sensor sends its **raw AD value** (`soilMoistureAd`, 9 bit; also MQTT and Loxone `rfN_soilMoistureAd`). An optional **two-point calibration** per sensor (`…:ad=<AD in dry soil>-<AD in water>` in the per-sensor calibration) replaces the sensor's own % with `(AD − AD0) × 100 / (AD100 − AD0)`, clamped to 0–100 — everywhere, including the Home Assistant entity.
- **External power (WS90 / WS80):** with firmware 1.6.0 and newer a WS90 on an external power supply reports a battery voltage of 0 V (Ecowitt wiki by Gyvate, section WS90; the WS80 likely the same) — shown as *external power* (`externalPower`), not as a low battery.
- **Lightning (WH57):** `lightningCount` is the sensor's raw 8-bit strike counter (shown only as a small *counter*). The node counts **strikes today**, **in the last hour** and the **time of the last strike** from its increments: the first packet after a start is the baseline, the 255 → 0 wrap is handled, a jump of more than 50 strikes in one packet is taken as a counter reset (battery change) and not counted. RAM only, like the rain.
- **Battery:** sensors that send their voltage show it (`batteryV`, status page); *battery low* follows the model's threshold (WH51: below 1.3 V on one AA — rechargeable NiMH cells at 1.2 V read as low; WN32P: the sensor's low-battery flag, the same bit as the WH25).

## Davis wireless (experimental)

**New, not yet tested with a real station.** The EU versions (868 MHz) of the **Davis Vantage Pro2 / Vantage Vue ISS** and the **anemometer transmitter 6332** can be received with the Heltec's SX1262 — no extra hardware. Set *Wireless sensors* on and *Wireless sensor type* to **Davis Vantage Pro2 / Vue (exclusive)** (web settings *Measurement*, portal field `rfproto` = `17`, parameter 50 = `17`). *Auto (search)* never picks Davis.

How it works: the ISS sends a 10-byte packet every 2.5625 s (ID 1) … 3.0 s (ID 8), each on the next of 5 channels (868.06–868.54 MHz). The node parks on one channel until the transmitter comes by (at most ~15 s), then follows the hop sequence: it moves to the next channel right after each packet and predicts the next one from the measured period. After 12 missed packets in a row it searches again. Details, protocol table and sources: [`lib/DavisSensorReceiver/README.md`](../lib/DavisSensorReceiver/README.md).

**Limits — Davis is an exclusive mode:**
- **LoRaWAN is paused** (no uplinks, no join) while Davis is selected — the status page says *LoRaWAN paused: Davis mode*. Outputs via Wi-Fi only: dashboard, `/api/data`, MQTT / Home Assistant, weather networks, Loxone.
- **No other wireless sensors** (Bresser, IT+, Fine Offset) at the same time; one Davis transmitter (ID), the first one heard or the ID set.
- Values: temperature (digital sensor), humidity, wind (speed in whole mph, every packet; the gust is the highest packet value of the interval), rain (bucket-tip counter → running total with the collector size 0.2 mm or 0.01 in), UV index, solar radiation (`solarWm2`, and as an approximate illuminance of 126.7 lx per W/m² for the *light* source), battery-low flag, Vue super-capacitor voltage. The ISS's own rain rate and 10-min gust are shown as diagnostics only. They appear as wireless sensor **`DA0000ii`** (ii = transmitter ID) in the wireless-sensor table and feed the [value sources](#value-sources) like any wireless sensor; every value arrives every ~10–50 s, well inside the 5-minute freshness window.
- Not supported: analog-thermistor temperature (very old ISS), soil/leaf stations, repeaters, US/AU bands (other channel tables).

**Settings** — web settings, section *Davis (diagnostics)* (shown while Davis is selected); all **live**, no restart or reflash:

| Setting | Meaning | Default |
|---------|---------|---------|
| Transmitter ID | 1–8 as set on the ISS DIP switches (console: transmitter ID); 0 = the first one heard | 0 |
| Station | Vantage Pro2 / 6332 or Vantage Vue (wind-direction formula) | Pro2 |
| Rain collector | 0.2 mm (EU) or 0.01 in | 0.2 mm |
| Frequency offset | −100…+100 kHz, added to every channel | 0 |
| Search: offset scan | while searching, also try ±6, ±12, … kHz up to this span (~15 s per step) | ±30 kHz |
| AFC while tracking | every 4th packet listens 6 kHz above / below and follows a drifting transmitter in 1.5-kHz steps | off |
| RX window: late / guard: early | a packet may arrive this much after / before the prediction | 25 / 40 ms |
| Channel table | measured 2026 (default) or the classic DavisRFM69 table | measured |
| Receiver bandwidth | 58.6–234.3 kHz | 93.8 kHz |
| Sniffer | every packet to the log | off |
| Raw capture + channel | park on one channel, no hopping, log everything that passes the sync word | off, ch0 |

**Sniffer and diagnostics**
- **Status page box *Davis***: state (ACQUIRE / TRACK / LOST / RAW), transmitter ID, sync % (tracked slots with a packet), last packet age and RSSI, packets / CRC errors / other / misses, current channel and frequency, measured period, offset set / in use, and the last packet of every message type (decoded value + raw bytes).
- **JSON**: `davis` object in `/api/data` and the MQTT data topic (see [`data.schema.json`](api/schemas/data.schema.json)).
- **Sniffer on** → one line per packet in the [web log](web-dashboard.md) (`/api/log`):
  `DV <s.ms> ch<n> <MHz> <offset>k <RSSI> dBm <result> id<n> <type> | <10 bytes firmware order> | air <10 bytes as received> | wind … | <value> | dt <ms> | <state>` — result `ok`, `CRC-FAIL`, `other-id`, `repeater`, `bad-trailer`, `out-of-window`; `dt` = arrival minus prediction. Misses (`MISS`) and search steps too, and a **summary every minute** (packets, CRC fails, misses, sync %, state, period, offset, RSSI; every 10 min without sniffer). The web log keeps only ~8 KB: at most 30 packet lines per minute go there, **all lines** go to the [radio trace](#capturing-a-radio-trace-for-us): Davis mode starts an open-ended one by itself (unless a trace is already running), download it from the log page or at **`/api/davis/log`** (last ~24 KB, same password as the log).
- **Raw capture** (when tracking does not work at all): parks on one channel and logs every packet that passes the sync word incl. CRC failures. Every 5th packet of the transmitter lands on that channel (~13 s). CRC failures with a strong RSSI = right channel, wrong frequency → change the offset in 3–5 kHz steps until `ok` appears; nothing at all = wrong channel table / far off frequency / out of range.

### Field-test checklist

**Take along:** Heltec V4 or V3 with an **external 868 MHz antenna** (never run without one), USB-C **data** cable, power bank, laptop with the repository and PlatformIO, phone with hotspot (the node joins it via Wi-Fi; the laptop too). Ask the owner for the console's **transmitter ID** and to show the console values during the test.

**Distance:** start 20–50 m from the ISS with line of sight, later 100–300 m.

1. **Flash** the current build: `~/.platformio/penv/bin/pio run -t upload`, then `pio device monitor` (115200 Bd) to see the IP address.
2. **Wi-Fi via the hotspot:** portal (hold the button 3 s) → hotspot SSID; open `http://<ip>/` from the laptop/phone in the same hotspot.
3. **Settings → Measurement:** *Wireless sensors* on, *Wireless sensor type* = *Davis (exclusive)*, save. Section *Davis (diagnostics)*: transmitter ID, station, sniffer **on**, save.
4. **Watch** the status page box *Davis* (reloads every 30 s) and `/api/log`: within ~15 s ACQUIRE → `locked on transmitter ID …` → TRACK; sync should be > 90 %.
5. **Tune if needed:**
   - stays in ACQUIRE, no `CRC-FAIL` lines: raise the offset scan to ±60 kHz; try the *classic* channel table; check ID and antenna; move closer.
   - `CRC-FAIL` lines with good RSSI (> −100 dBm): frequency off — note the *offset in use*, set it as *frequency offset*, fine-tune in 2–3 kHz steps; switch on AFC.
   - TRACK with many misses and `dt` near the window limits: raise *RX window* / *guard* (e.g. 60 / 80 ms); `out-of-window` lines: a second station with the same ID nearby.
   - nothing helps: **raw capture** on ch0, then ch1 …, offsets −30…+30 kHz in 5-kHz steps; note which combination gives `ok` or `CRC-FAIL`.
6. **Compare values** with the console at the same moment (temperature, humidity, wind, rain counter; with the owner's permission tip the rain bucket once → the counter in message E rises by 1 and the rain total by 0.2 mm). Write down the console values with the time.
7. **Save the logs** before leaving: `http://<ip>/api/log/raw`, the radio trace (`http://<ip>/api/rf/trace`, or `/api/davis/log`) and `http://<ip>/api/data` (e.g. `curl --digest -u admin:<password> …`); note temperature, distance and antenna position. Repeat at the second station.
8. Afterwards: *Wireless sensor type* back to your sensor (LoRaWAN resumes by itself).

**Phantom rain:** the ISS sends a 7-bit tip counter. A corrupt packet that still passes the CRC, a counter reset or a step backwards would otherwise show up as rain; the phantom-rain filter (*Davis (diagnostics)*, on by default) holds an implausible jump until the next counter packet confirms or contradicts it and logs every case — see [Settings](settings.md#settings-reference).

## Capturing a radio trace for us

When a sensor is not recognised, shows wrong values or is received only now and then, a **radio trace** tells us what it actually sends. The node records **every packet** its receiver gets, in every receive phase (Bresser, IT+ 17.241 and 9.579 kbit/s, the Fine Offset / IT+ 17.241 kbit/s phase, Davis) — also packets that fail their checks (CRC, checksum, digest) or come from a sensor family the firmware does not know, which is exactly what we need.

1. Open the **log page** (`/api/log`, admin password; linked from the status page, row *Radio trace*), box **Radio trace**.
2. Choose the duration (**5 / 15 / 60 min**) and what to record: **all packets**, **only unknown / failed packets** (best for "my sensor is not recognised"), or **only this ID** (one sensor that misbehaves). Press **Start capture** (the browser asked for the admin password, user `admin`, when you opened the page).
3. Leave the node alone for the duration (the log page — reload it — and the status page show packets, buffer fill and the time left; *Stop* on the log page ends it early). Keep the sensor's display / console at hand and note what it shows.
4. Press **Download diagnostic file** — `uwn-rftrace-<hostname>-<YYYYMMDD-HHMM>.txt` — and send it to us with a short description (sensor model, what is wrong, what its own display shows).

What is in the file: firmware version, board, the receive settings (sensor type, ID list, LoRaWAN on/off), the sensor table, statistics per receive phase and per sensor ID for the **whole** capture — for sensors with a known send interval also how many of the expected transmissions arrived (e.g. `5 of 6 sent (83 %)`; the repeat several sensors send ~60 ms later is not counted twice) — and how long received packets waited for the firmware (*read delay*; a packet arriving meanwhile replaces an unread one), then one line per packet: uptime and local time, phase, RSSI, result (`OK`, `IGNORED` = not in the ID list / table full, `FAILED` = known format but a check failed, `UNKNOWN`, `EVENT`), protocol, model, ID, the check result, decoded values and the raw bytes in hex.

**Unknown frames:** while a capture runs, the Fine Offset / IT+ phase reads **64 bytes** per frame instead of 32, so longer unknown frames (e.g. the Ecowitt IoT devices' two-way `B9` frames) appear complete in the file; known frames are cut to their real length as before. After the capture the node reads 32 bytes again (each read keeps the receiver busy about 15 ms longer while capturing).

**Privacy:** the file contains the IDs and readings of **all sensors in range — also your neighbours'**. It never contains passwords or keys (Wi-Fi, MQTT, admin, LoRaWAN, weather networks) or your coordinates.

**Memory:** the capture uses about 26 KB of RAM, reserved only when you start it (refused with a message if the free memory is too low) and kept after it ended so you can download it — until you press *Discard*, start a new one or restart the node. The ring keeps the newest ~24 KB of lines (about 150–200 packets); with *all packets* and many sensors the oldest lines are overwritten (the header says how much) — use a filter or a shorter duration. Scripts: `POST /api/rf/trace` (`action=start&minutes=15&filter=problems`, `stop`, `clear`) and `GET /api/rf/trace` (`?status` for the progress), Digest authentication, see the [OpenAPI file](api/openapi.yaml).

## Value Sources

Board sensors and wireless sensors can measure the same quantities. For each group one setting (web settings *Measurement*, portal field `srcs`, parameters 45–49 and 54) decides which sensor feeds **all** outputs — LoRaWAN, `/api/data` / MQTT, Home Assistant, weather networks, history, display:

| Group | Board sensor | Wireless sensors |
|-------|--------------|------------------|
| Temperature / humidity | BME280 | Bresser 5/6/7-in-1, thermo/hygro; TFA / LaCrosse IT+ (humidity only if the sensor has it); Ecowitt / Froggit WH65/WS69, WS68/80/85/90, WH31 (WN34/WN38: temperature only); Davis ISS |
| Wind (mean, gust, direction always together) | Davis anemometer + vane | Bresser 5/6/7-in-1; Ecowitt / Froggit WH65/WS69, WS68/80/85/90; Davis ISS / 6332 (wireless) |
| Rain | tipping-bucket gauge | Bresser 5/6/7-in-1; Ecowitt / Froggit WH65/WS69, WS85/90, WH40, WN20; Davis ISS |
| UV | analog UV input (PCB v2.0) | Bresser 6/7-in-1 (UV index); Ecowitt / Froggit WH65/WS69, WS80/90; Davis ISS with UV sensor |
| Light | – | Bresser 7-in-1 (lux); Ecowitt / Froggit WH65/WS69, WS80/90; Davis solar radiation (approximated as lux) |
| Pressure | BME280 | Ecowitt / Froggit **WS69** with pressure module and **WN32P / WH25 / WH32B** (indoor — fine for pressure, *Auto* takes them). Not: Bresser, IT+, Davis (the ISS has no barometer; the console's is not on the radio) |

The DS18B20 probes, wind 2 and AUX are unaffected.

- **Pressure:** the sensors send their **station (absolute) pressure**; the node reduces it to sea level (QNH) with the configured *altitude* using exactly the formula of the BME280 path, so `pressureAbs` / `pressureQnh`, the 3-h tendency and weather trend, history, Home Assistant, the weather networks, LoRaWAN and the display work the same with either source. Set the altitude of the **sensor** (for an indoor WN32P: of the room). *Auto* = BME280 if detected (existing nodes behave exactly as before), else the first ★ sensor (in their order; without ★: wireless 1–4) with a pressure value not older than 5 min; for pressure *Auto* also takes indoor sensors. Switching the source can step the pressure history by the sensors' calibration difference.

- **Auto** (default) works like a PC boot order: the board sensor first (if enabled / detected), then **your ★ sensors in their order** — the order of the ★ list, set with the arrows on the settings page; the first one that currently delivers the value is used, so ★ 1 is the main sensor and the ones after it are fallbacks. Sensors that are not ★ (neighbours) are never used while any sensor is ★. **Without ★ sensors** *Auto* looks at wireless 1–4 (never 5–32): If several of wireless 1–4 deliver the same group, **Ecowitt's own sensor order** decides (Ecowitt wiki by Gyvate, section "sensor hierarchy"): temperature / humidity WN32 / WH32 outdoor > WS90 > WS80 > WS69 / WH65; rain WH40 > WN20 > WS69 / WH65 (tipping buckets) > WS90 / WS85 (piezo); wind WS90 > WS80 > WS85 > WS69 / WH65 > WS68; UV / light WS90 > WS80 > WS69 / WH65 > WS68. Other sensors (Bresser, IT+, Davis, other families) and equal ranks keep the order of their numbers. For temperature / humidity *Auto* skips **indoor sensors** (Ecowitt WH45 / WH46 air-quality sensors and the WN32P / WH25 indoor thermo-hygro-barometer, IDs `45…`, `46…`, `25…`): without an ID list such a sensor could otherwise land in wireless 1–4 and feed the outdoor temperature. Choose *Wireless n* explicitly if you really want one of them. A wireless sensor counts as long as its last packet **with that value** is at most **5 minutes** old (sensors that send only every 10 minutes — WH41 / WH43 PM2.5 and WH45 / WH46 on battery — 25 minutes, 2.5 × their interval; the same window marks their values stale and their Home Assistant entities unavailable) — judged per value, so a dead or out-of-range sensor drops out automatically, and so does a single failed measurement of a sensor that keeps sending the others. With only the board sensors (no wireless sensors) *Auto* behaves exactly as before.
- **Board sensor** / **Wireless n** use exactly that sensor and nothing else; if it does not deliver, the value is left out (no fallback). *Off* never reports the group.
- **Wireless n** is sensor number n (1–32): the ★ sensors first in their order, then the others in the order they were first received. Any of them can be chosen; the lists offer the sensors that exist (received or ★), with their name and ID. *Auto* only looks at 1–4, so a neighbour's sensor further down never becomes a source by itself — put the sensors that should feed the outputs first (★ and arrows). Parameter values: `2`–`33` = wireless 1–32, `34` = off.
- **Wind** from a wireless sensor uses the sensor's own mean, gust and direction per packet (every 12–16 s), aggregated per send path exactly like the board anemometer: *Interval* (time-weighted mean, highest gust, vector-mean direction since the last send) or *10 min*. The weather networks get the 10-min values. The gust is the sensor's gust, not the board's 3-s gust.
- **Rain**: the running total (*rain since start*) only adds the increases of the selected source — the board's tipping-bucket pulses or the difference between two packets of the wireless sensor's total. Switching the source never produces a jump; a battery change of the wireless sensor (its total restarts) counts from zero again. Missed packets (during an uplink, interference, weak signal) lose no rain: the sensor sends its total, so the next packet received carries the increase — after a gap of more than 5 minutes the missed rain is added gradually (at its average rate over the gap, within at most 1 h), so the total stays right without a rain-rate spike.
- **Where the value came from** is visible on the status page (*Sources*, while wireless sensors are on or a source is set other than *Auto*), in JSON as `sources` (`{"tempHum": "board", "wind": "radio:39582376", …, "light": "none"}`, plus `radioBatteryLow` when a wireless sensor in use reports a low battery) and in the LoRaWAN payload (CayenneLPP Ch 16 / binary field 33) — these three only while wireless sensors are on.
- Not (yet) sent to the weather networks: UV and light.
